# Renderer backends

The engine draws through `gpg::gal`, the GPG abstraction layer. The shipped binary had Direct3D 9 (default) and Direct3D 10 (`/D3D10`); this fork adds Direct3D 11, Direct3D 12 and Vulkan, and by default takes the newest one that starts.

*Snapshot: 24/10/2026.*

| Switch | Backend | Effects | Code |
|---|---|---|---|
| `/d3d9` | Direct3D 9 | D3DX9 effect framework | `src/gpg/gal/backends/d3d9` |
| `/D3D10` | Direct3D 10, as shipped | D3DX10 | `src/gpg/gal/backends/d3d10` |
| `/d3d11` | Direct3D 11 | Effects 11 (FX11), `fx_5_0` | `src/gpg/gal/backends/d3d11` |
| `/d3d12` | Direct3D 12 | FAF effect layer, DXIL via DXC | `src/gpg/gal/backends/d3d12` |
| `/vulkan` | Vulkan 1.3 | FAF effect layer, SPIR-V via DXC | `src/gpg/gal/backends/vulkan` |

## Choosing the renderer

Players pick it under Options, Video, **Graphics API**: Automatic, Direct3D 9, Direct3D 11, Direct3D 12 or Vulkan. The choice is stored as the option `graphics_api` (`auto`, `d3d9`, `d3d11`, `d3d12`, `vulkan`; default `auto`) in the profile's options, like `vsync`.

| Choice | Renderers tried, in order |
|---|---|
| `auto`, unset, unknown value (x64) | Direct3D 12, Vulkan, Direct3D 11, Direct3D 9 |
| `auto`, unset, unknown value (x86) | Direct3D 11, Vulkan, Direct3D 12, Direct3D 9 (see [Known issues](#known-issues)) |
| `d3d12` / `vulkan` / `d3d11` | That one, then Direct3D 9 |
| `d3d9` | Direct3D 9 |

- **Command line wins:** `/d3d9`, `/d3d11`, `/d3d12`, `/vulkan` override the option the same way; `/D3D10` is tried alone.
- **Fallback:** a renderer counts once its device is created and set up. One that cannot start is logged with the reason, and the next is tried with the same window settings (`CScApp::CreateDevice`, order from `RendererAttemptOrder`).
- **Restart needed:** the option is read once at startup (`OPTIONS_GetString`), so changing it raises the options screen's standard "requires a restart" dialog (`restart = true`), whose OK saves and exits. Switching renderers without a restart is not supported: the existing device rebind (`CD3DDevice::InitContext`, used for resolution, vsync and anti-aliasing changes and for a lost device) resets the *same* gal device, recreating only what a Direct3D 9 reset loses and keeping file textures, static buffers and compiled effects.
- **Window title** names the renderer in use (`Forged Alliance [Vulkan] ...`; no tag for Direct3D 9). `/title <label>` appends a label, to tell side-by-side test windows apart.
- **Testing the chain:** `FAF_GAL_FAIL_SETUP=1` fails every newer backend; a list such as `d3d12,vulkan` fails only those (Direct3D 12 and Vulkan read the list, Direct3D 11 only `1`).

The log shows each step:

```
graphics_api option: auto
renderer: trying Direct3D 12
GAL Exception: ...                      (the reason it failed)
Direct3D 12 is unavailable; falling back to Vulkan
renderer: trying Vulkan
Vulkan: ready (...)
```

### Where the option comes from

The options entry comes from the engine's own Lua, never from edits to FAF's gamedata:

- **Source:** `data/fafengine/` holds engine-owned scripts that extend gamedata scripts. The build copies it next to the executable (`src/CMakeLists.txt`), and `build.ps1` copies it into the run folder.
- **Mount:** at startup the engine mounts `<exe folder>/fafengine` at `/fafengine` and registers it as a hook directory, after the init file's own `path` and `hook` entries (`AppendEngineHookFolder` in `src/moho/misc/StartupHelpers.cpp`). The engine does this itself because the init files (`init_faf.lua` and the rest) belong to the FAF client.
- **Hook:** a hook file is appended to the gamedata file of the same path, so `fafengine/lua/options/options.lua` runs at the end of `/lua/options/options.lua` and inserts the entry after Vertical Sync. The log says `engine hooks: ... mounted at /fafengine` and `Hooked /lua/options/options.lua with /fafengine/lua/options/options.lua`.
- **Modules:** files that only the hooks import (the replay timeline and its controls) lie under `data/fafengine/modules/`, a path no gamedata file has. Under `lua/` they would be taken as hooks of a FAF file of the same name and appended to it.
- **In FAF's Lua:** the same options and screens are to come with FAF's own Lua behind `GetEngineInfo`, which only this engine has (issue #327). When FAF's files carry them, the hooks here leave them out: an option whose key is already in the tab, the timeline when `/lua/ui/game/replay_timeline.lua` exists, the rejoin screen when `uimain.lua` defines `UpdateRejoinScreen`, the Connectivity rows when `disconnect.lua` defines its own `GetSessionClients`.

## Effects: one source, translated at load time

The game's `.fx` files are user data. They are never copied into this repository; the ports below run on them at load time.

1. **Preprocess** with the Direct3D 10 macros (`technique` becomes `technique10`, `vs_3_0` becomes `vs_4_0`, and so on) and `d3d10states.compat` prepended (`CD3DEffectTechnique`), using `D3DPreprocess` from d3dcompiler_47.
2. **Override layer** (`backends/d3d11/EffectSourceD3D11.cpp`) rewrites the D3D9-isms the effects still have: D3D9 pass states become state objects, `sampler1D` and `tex1D` become 2D, shader inputs are re-linked, and the D3D9 fixed-function vertex shader is emulated for pre-transformed vertices. Fixes go here, never into the gamedata.
3. **Direct3D 11** compiles the result as `fx_5_0` and loads it into Effects 11.
4. **Direct3D 12 and Vulkan** hand it to the FAF effect layer (`src/gpg/gal/effects`):
   - `EffectDescription`: techniques, passes, annotations (constant expressions folded), blend, depth-stencil and rasterizer states, sampler states, and parameters with their defaults.
   - `ModernHlsl`: plain HLSL. Techniques and states are removed; the FX9 sampler model becomes `Texture2D`/`TextureCube`/`Texture3D` plus `SamplerState` on fixed registers; parameters a function writes get local copies; stage boundaries get `SV_` semantics. One wrapper entry point per (stage, function, compile-time arguments). The predicted `$Globals` layout matches DXC's reflection for every entry point.
   - `ShaderCompiler`: DXC (`dxcompiler.dll`), shader model 6.0, `-HV 2018 -Zpr`, producing DXIL or SPIR-V (`-fvk-use-dx-layout`).
   - `EffectParameters`: the `$Globals` image, written with Direct3D 9 / Effects 11 setter semantics and snapshotted when a pass begins.
   - `EffectRuntime`: the gal `Effect`/`EffectTechnique`/`EffectVariable` shared by both backends. Vulkan links stages by location while DXC numbers each shader's interface on its own, so `SpirvReflect` matches vertex inputs and the vertex-to-pixel interface by HLSL semantic. Shaders compile on first use and are cached in `%LOCALAPPDATA%\FAForever\ShaderCache` (or `FAF_SHADER_CACHE_DIR`).

**Why DXC:** Slang and DXC were both tried on the real effects. Both reject raw FX9 texture/sampler syntax, so a modernisation pass is needed either way. After that pass DXC compiled all 339 entry points of the 11 effects to DXIL and to SPIR-V; Slang failed most entries of `water2`, `particle` and `terrain`, mostly on implicit vector truncation and writes to globals, which FXC-era HLSL relies on.

### D3D9 behaviour restored

The D3D10 state packs lost some of what D3D9 did; the newer backends restore it:

- **Clear** covers the viewport (clipped to the targets), not the whole target.
- **Viewport reset:** binding a different colour target resets the viewport to the whole target (D3D9's `SetRenderTarget`). The engine clears the shadow map before it sets a viewport; without the reset, part of it keeps stale depth.
- **Depth clipping** is always on (`d3d10states.compat` turns it off, which lets shadow casters outside the light's range clamp onto the map).
- **Depth bias:** the compat file's fractional `DepthBias` values are D3D9 depth-range fractions, converted to 24-bit depth steps (fxc truncates them to 0, and the ground decals then z-fight the terrain).
- **Alpha blending:** the alpha channel blends with the colour factors (D3D9 had separate alpha blending off). The compat file sets `SrcBlendAlpha = ONE`, `DestBlendAlpha = ZERO` on every state, which overwrites the frame's alpha, and that alpha is the glow mask: the commander's warp-in light then lit its whole quad as a hard-edged rectangle.
- **Pixel centres:** Direct3D 9 puts them on integer coordinates, Direct3D 10+ and Vulkan on halves, and the engine draws for D3D9 (the UI projection `CD3DPrimBatcher::SetToViewport` shifts quads by -0.5 pixel). Every backend therefore moves the native viewport origin by +0.5 pixel (`Direct3D9PixelCentreShift`); without it UI text sampled between texels and looked doubled. The fixed-function emulation's `faf_ViewportSize` takes the same shift.
- **Alpha test:** effects still set `AlphaTestEnable`, `AlphaFunc` and `AlphaRef` in their passes, inside `#ifndef DIRECT3D10`, and FAF's water shader relies on it (`HighFidelityPS` returns the land mask in alpha, and `NotEqual 0` discards it). The effect layer reads these states from the original source (`ApplyDirect3D9PassStates`) and the pixel entry discards as D3D9 did, on the 8-bit alpha. The effects' own `AlphaTestD3D10` helper, which D3D9 never ran, is emptied. Without the alpha test the water drew over the land as grey polygons when zoomed out.
- **Technique begin state** culls nothing, as Direct3D 9's does (`PipelineStateD3D9::BeginTechnique`); the D3D10 pack culls back faces. A pass that sets no cull mode draws with it: the low and medium fidelity water passes are such passes, and with culling their map-sized quad was dropped, which left the seabed showing untinted, dark, and without wave crests.
- **Shader math** as shader model 2/3 compiled it: `sqrt`/`rsqrt` of `|x|`, and `pow` of `|x|` (sign kept for odd integer exponents). Shader model 4 and 6 return NaN for a negative operand, and a NaN blended into a target stores zero. Direct3D 12 and Vulkan get this from `#define` macros that DXC expands; Direct3D 11 compiles with fxc, whose preprocessor leaves a macro alone when its replacement contains its own name (`#define sqrt(x) sqrt(abs(x))` did nothing there), so the translator emits helper functions (`faf_sqrt`, `faf_rsqrt`, `faf_pow`, defined before the macros that name them). Before this the UEF shield was black on Direct3D 11: its normal reconstruction `sqrt(1 - dot(xy, xy))` is negative for its secondary texture.
- **Missing vertex inputs** (ones a vertex format lacks) read as zero.
- **Feedback:** a pass that samples the target it draws into reads zero, as on D3D10/11.

## GPU-driven paths

The GPU-driven renderers (strategic icons with GPU classification, fog of war, instance streams) use the small binding model in `src/gpg/gal/GpuDriven.h`: one constant block, four read buffers, two textures, two write buffers and one sampler. Every newer backend implements all of it.

| | Programs | Binding |
|---|---|---|
| Direct3D 11 | d3dcompiler `vs/ps/cs_5_0` | Registers b0, t0..t5, u0..u1, s0 directly |
| Direct3D 12 | DXC `vs/ps/cs_6_0` (`ShaderCompiler::CompileRaw`) | One root signature per sampler kind: root CBV b0, SRV table t0..t5, UAV table u0..u1, static sampler s0; `ExecuteIndirect` for indirect draws (`d3d12/GpuDrivenD3D12.cpp`) |
| Vulkan | DXC SPIR-V with `-fvk-b-shift 0 -fvk-t-shift 1 -fvk-u-shift 7 -fvk-s-shift 9` | One descriptor set, bindings 0..9; `vkCmdDrawIndirect`; compute outside the rendering scope (`vulkan/GpuDrivenVulkan.cpp`) |

GPU timestamps feed `RenderProfiler` (`FAF_GPU_PROFILE=<frames>`). `FAF_ICON_GPU_CHECK=<n>` compares every n-th GPU-classified icon frame with the CPU path, record by record.

### Turning the paths on

Each path has a console variable with three values: `-1` (default, auto: on only where the backend reports both the features the path needs and the path's verified bit), `0` (off: the original draw path), `1` (force on wherever the features exist, for testing a backend before it is verified). Two `gal::Device` queries decide it (`src/moho/render/GpuPathSettings.cpp`):

- **`GetGpuDrivenFeatures()`**: what the backend can do (`GpuDrivenFeature` bits: vertex pulling, compute, indirect draws, timestamps, buffer copy).
- **`GetGpuDrivenVerified()`**: the `GpuDrivenPath` bits the backend has passed parity on. The base `Device` returns 0, so a backend that does not override it draws everything the original way under auto.

| Console variable | Path bit | Needs |
|---|---|---|
| `ren_GpuIcons` | `kGpuPathStrategicIcons` | Vertex pulling |
| `ren_GpuIconClassify` | `kGpuPathIconClassify` | Vertex pulling, compute, indirect draws (also needs `ui_IconRecords`) |
| `ren_GpuFog` | `kGpuPathFogOfWar` | Vertex pulling |
| `ren_GpuSelectBrackets` | `kGpuPathSelectBrackets` | Vertex pulling |
| `ren_ParticleBatch` | `kGpuPathParticleBatch` | Buffer copy (`Device::CopyVertexBufferRegion` on the GPU) |
| `ren_GpuProjectileIcons` | `kGpuPathProjectileIcons` | Vertex pulling |
| `ren_GpuShapes` | `kGpuPathWorldShapes` | Vertex pulling |
| `ren_GpuRanges` | `kGpuPathRanges` | Vertex pulling |
| `ren_GpuText` | `kGpuPathMsdfText` | Vertex pulling |
| `ren_GpuFontCook` | `kGpuPathMsdfCook` | Vertex pulling, compute |

- **Direct3D 9** reports no features, so every path is off there whatever its variable says.
- **Direct3D 11, 12 and Vulkan** report all features and every verified bit except `kGpuPathMsdfCook`, which they report only for an NVIDIA adapter (`kPciVendorNvidia`) until its atlases are compared on AMD and Intel GPUs too (issue #309; elsewhere fonts cook on the CPU), `kGpuPathParticleBatch`, which stays out until a paused screenshot A/B of `ren_ParticleBatch` is clean at several zooms (one showed extra particle specks with it on), and `kGpuPathRanges`: its paused A/B is pixel-identical on Direct3D 12 and Vulkan (`tools/scenarios/1p-ringgpu-main.yaml`, `1p-ringgpu-vulkan.yaml`), but with `range_ViewCull` on it makes the range pass slower, not faster (see [Switches](SWITCHES.md)).
- **Verifying a path:** a backend turns a path on by default by adding its bit to `GetGpuDrivenVerified()` once it passes that path's checks (the self-check readback where one exists, and a same-process screenshot A/B against the variable at 0); no variable or default changes.
- **Log:** the resolved state is logged once at startup and by `ren_Info`, as `GPU-driven paths: ren_GpuIcons=auto:on, ...`.
- `ui_IconRecords` and `ren_CacheFogFootprint` are CPU-side and on by default on every backend. All of these variables are also listed in [Switches](SWITCHES.md).

## Toolchain setup

Configuring the CMake build fetches all three into `dependencies/` (`cmake/FafDependencies.cmake`):

- **FX11 (Direct3D 11):** git submodule `dependencies/FX11`, `microsoft/FX11` at `bec3b8fc`. The engine compiles FX11's sources directly (C++17, two-phase lookup off).
- **DXC (Direct3D 12, Vulkan):** the [DirectXShaderCompiler release](https://github.com/microsoft/DirectXShaderCompiler/releases) v1.9.2609 (`dxc_2026_09_29.zip`, SHA256-pinned), unpacked to `dependencies/dxc`. At run time the game loads `dxcompiler.dll` and `dxil.dll` (the DXIL signer) from its own directory, from `FAF_DXC_DIR`, or else from the copy the executable carries (issue #315): the build packs both DLLs into the exe (10.4 MB compressed on x64), and the first start of Direct3D 12 or Vulkan unpacks them into `%LOCALAPPDATA%\FAForeveraf-re\dxc-<hash>\`. DLLs next to the executable win, so a different DXC can be tried without a rebuild.
- **Vulkan headers (Vulkan):** git submodule `dependencies/vulkan`, `KhronosGroup/Vulkan-Headers` at `v1.4.304`. The game loads `vulkan-1.dll` (installed with the GPU driver) at run time and links no import library, so x86 and x64 both build from the headers alone.

### Runtime requirements

Both are optional; without them the game falls back to Direct3D 9.

- **D3DX11:** `/d3d11`, `/d3d12` and `/vulkan` decode textures with D3DX11 (`d3dx11_43.dll`, from the DirectX End-User Runtime of June 2010), as the shipped D3D10 path did with D3DX10. Direct3D 12 and Vulkan run it on a private WARP device (`backends/common/ImageCodec`). Without `d3dx11_43.dll`, Direct3D 12 and Vulkan decode with DirectXTex instead (`backends/common/ImageCodecDirectXTex.cpp`, issue #318): the same formats, sizes and mip counts, and every level a file has byte for byte; the levels D3DX11 builds for a file without them come out within about 30-48 dB of D3DX11's (the two filter and BC-encode differently), and screenshots differ less than two D3DX11 runs of the same scene. Wine's own `d3dx11_43.dll` decodes from version 11.0 on and doesn't save; Direct3D 12 and Vulkan write the DDS files they need themselves when it says so. `/d3d11` doesn't start on Wine 11.0 as it comes: Wine's compiler refuses its built-in effect, and that backend calls D3DX11's save directly.
- **Direct3D 12** needs Windows 10 (d3d12.dll is loaded at run time).
- **Vulkan** needs a Vulkan 1.3 driver with dynamic rendering, synchronization2, timeline semaphores, scalar block layout (`$Globals` keeps Direct3D's packing) and BC textures. It runs windowed or borderless only (no exclusive full screen).

## Known issues

- **Direct3D 12 in the 32-bit build, NVIDIA** (seen on a TITAN RTX, driver 32.0.15.7270): after minutes of play the GPU takes an SM MMU fault (`Graphics SM Warp Exception ... MMU Fault`, Xid 13 in the System event log) and the device is removed as hung (`0x887A0006`). It shows on any draw or dispatch (the bloom extract `frame.fx:TCopyGlowingStuff` and `StrategicIconClassify` most often), right after a submission split mid-frame by upload pressure, and is much more frequent with `FAF_GAL_UPLOAD_SUBMIT_KB=1024`. The debug layer, GPU-based validation and anything that slows the CPU hide it; the x64 build of the same code runs the same load cleanly. No application error was found (see the investigation notes in the commit), so `auto` starts the 32-bit build with Direct3D 11. It stays available with `/d3d12` or `graphics_api = d3d12`.
- **Vulkan on NVIDIA:** `PrintWindow(PW_RENDERFULLCONTENT)` on the game window (some capture tools do this) makes `PeekMessage` report a message that `GetMessage` then never returns. The engine's loop (`WIN_AppExecute`, as shipped: `Pending()` then `Dispatch()`) sleeps in `GetMessage` until the next input, so the game stands still until the mouse moves. Any posted message wakes it; the test scripts post `WM_NULL` after each capture.
- **`/D3D10` crashes at startup** on both x86 and x64, as shipped: `DeviceD3D10::SetupDXGIDevice` copies an `AdapterD3D10` without AddRef, so the temporary's destructor releases the adapter and its outputs, which the code then uses after they are freed. It is left as the binary had it.

## Vsync and swap-chain handling

Reports of crashes on vsync changes and presents on NVIDIA and Intel led to a read-through of every swap-chain path. The only GPU available for testing was an AMD RX 7900 XTX, so what follows says what was run and what was only reasoned.

**What changed**

- **D3D11 and D3D12: a Reset rebuilds only what changed** (`dxgi/DxgiSwapChainPolicy.h`, `PlanReset`). Vsync is only the present interval: when no chain differs (vsync, anti-aliasing, the same resolution set again) the back buffers stay and the Reset only hands back the start-up state. A windowed size change is a `ResizeBuffers`; a window-mode change (the head's full-screen flag, the full-screen size or refresh rate) builds a new chain, because the tearing flag and the display mode are fixed when it is made. A minimised window keeps its chain. The head's full-screen flag and refresh rate are now copied into the device context on a Reset (they were ignored).
- **A failed `ResizeBuffers` no longer throws from `CreateRenderTargets`.** `SwapChain::Reconfigure` retries once after the GPU is drained (D3D12: two submissions and a fence wait; D3D11: `ClearState` + `Flush`), then creates a new chain; a full-screen chain that cannot be made falls back to a windowed one, and as a last resort the previous chain is built again. Only when none can be made does the Reset throw (the engine's `InitContext` catches it as before). A removed device is passed to the existing recovery (D3D12: reason, DRED breadcrumbs, `gpg::Die`; D3D11: reason, exit).
- **Present results are classified** (`ClassifyPresent`). `DXGI_STATUS_OCCLUDED` is a success code: nothing waits, and the log says once when the window is occluded and when it is visible again. `DXGI_ERROR_MODE_CHANGE_IN_PROGRESS` and `WAS_STILL_DRAWING` drop the frame. `DXGI_ERROR_INVALID_CALL` with the tearing flag is retried once without it and tearing is then off for that chain; without the flag the chain is rebuilt through the engine's own Reset (`TestCooperativeLevel` answers 1, `CD3DDevice::Paint` rebinds the context), three times at most, then it throws as before. Device removed / reset / hung / driver error end in the existing recovery.
- **Chain creation drops optional flags before giving up.** A driver that refuses ALLOW_TEARING (or the frame-latency object) gets the same model without it before the next model is tried. The tearing flag stays consistent: it is set only for a windowed chain, `ResizeBuffers` passes the creation flags, the present flag is used only without vsync and outside exclusive full screen (asked from DXGI, because DXGI can leave exclusive mode by itself).
- **Frame latency (D3D11, D3D12), off by default.** `FAF_GAL_FRAME_LATENCY=1..3` makes the chain a `FRAME_LATENCY_WAITABLE_OBJECT` chain with that many frames queued at most (never more than the buffer count) and waits on the object after each present, before the next frame is recorded, for lower input lag with vsync. The wait is skipped while the window is occluded and gives up for good after three timeouts in a row; the object is made again after each `ResizeBuffers`. Without the variable the chain is exactly as before.
- **Vulkan:** the swap-chain code builds on the scaled present (`ren_VulkanScaledPresent`, on by default), where an out-of-date or suboptimal chain is made again at the window's size without the engine's help. Added: a minimised window (surface extent 0 x 0) keeps its swap chain instead of creating one with no area. A head that draws straight into the swap-chain images (`ren_VulkanScaledPresent 0`, or a surface format without blit support) cannot follow the window that way, so `VK_ERROR_OUT_OF_DATE_KHR` from acquire or present (and `VK_SUBOPTIMAL_KHR` when the window size no longer matches the chain) asks the engine for a Reset the same way as the D3D backends (`TestCooperativeLevel` answers 1, `CD3DDevice::Paint` rebinds the context), three times at most; `VK_ERROR_SURFACE_LOST_KHR` does this for every head. The present-mode choice stays upstream's ladder (a refused mode falls to the next, ending with FIFO). When every mode is refused, the chain is created once more without the old chain and, when the surface was lost, on a new surface. Vulkan fixes the present mode when the chain is made, so a Reset rebuilds a head's chain only when its size, the head's size or the first present mode vsync asks for differs; a vsync-only Reset with nothing different rebuilds nothing, as on D3D11 and D3D12.
- **Direct3D 9:** the present interval is a field of `D3DPRESENT_PARAMETERS`, so a vsync change needs `IDirect3DDevice9::Reset` by API design, and there is no flip chain, tearing flag or `ResizeBuffers` to get wrong. The Reset array of present parameters leaked on every call (the binary never freed it); it is freed now. A failed `Reset` is logged with its HRESULT and throws as the binary does.

**Verified on AMD (RX 7900 XTX, `/d3d12debug`, `/d3d11debug`, windowed 1600 x 900, `adaptive_acid_lakes`)**: on Direct3D 12, 11 and 9, Vertical Sync switched with `SC_VerticalSync` from a UI script four times, then 16 times in 4 s, then a maximise/restore pair twice (four `ResizeBuffers` between 1600 x 900 and 2560 x 1351 on D3D11 and D3D12), minimise and restore, and rapid window-size changes; no crash, no debug-layer or validation message about back buffers or swap chains, the vsync-only Resets rebuild nothing on D3D11 and D3D12 (and the log says so). Direct3D 12 also ran with `FAF_GAL_FRAME_LATENCY=2`: the wait is set up at creation and again after every resize, with no timeout. The pure decisions (`ClassifyPresent`, `PresentFlags`, `PlanReset`, the frame-latency clamp) have host tests: `cmake --build --preset clang-x64-release --target faf_dxgi_tests`, then `build/clang-x64-release/tests/faf_dxgi_tests.exe`.

**Reasoned only (no NVIDIA or Intel hardware)**: the tearing retry after `INVALID_CALL`, the `ResizeBuffers` retry and the chain recreation (nothing failed on AMD), exclusive full screen entered or left through a Reset, the hybrid-GPU present path (an Intel iGPU driving the display from an NVIDIA dGPU), a window moved to an output of another adapter, the occluded-present path, the frame-latency wait on a real NVIDIA / Intel driver, and the Vulkan changes above (minimised window, Reset request after out-of-date / surface-lost / mismatched-suboptimal, the creation retry, the unchanged-chain check): they were written onto the scaled-present code without a build, so none of them has been compiled or run. If a crash on those still shows up, the log now names the HRESULT and the step; `FAF_GAL_FRAME_LATENCY` stays unset unless the lower input lag is wanted.

## Diagnostics

| Switch / variable | Effect |
|---|---|
| `/d3d11debug`, `/d3d12debug`, `/vulkandebug` | API debug or validation layer; its warnings go to the game log |
| `/d3d12gbv` | Direct3D 12: the debug layer with GPU-based validation (very slow) |
| `/d3d12dred` | Direct3D 12: device removed extended data. On a device loss the log shows the breadcrumbs of the lists the GPU had started (each with the technique or GPU program it belongs to), numbered markers the GPU writes around every draw, dispatch and copy (the first unfinished one names the command that faulted or hung), and the allocation a page fault hit |
| `/d3d11blt` | Direct3D 11: legacy blt-model swap chain |
| `FAF_GAL_FRAME_LATENCY=<1-3>` | Direct3D 11, 12: frame-latency waitable swap chain with that many frames queued at most (default off); see "Vsync and swap-chain handling" |
| `FAF_GAL_MEMORY_LOG=<seconds>` | Direct3D 12: logs the backend's CPU copies, upload pages, upload-pressure submissions, passes carried into the next submission, submissions in flight and the address space left |
| `FAF_GAL_UPLOAD_SUBMIT_KB=<n>` | Direct3D 12: submits the recorded commands after every n KB of uploads (default 48 MB on x86, 96 MB on x64), which exercises the mid-frame submission paths |
| `FAF_CRASH_NO_DIALOG=1` | The crash report and minidump are written, but no dialog waits for a click (unattended test runs) |
| `FAF_GAL_FAIL_SETUP=1`, `=d3d12,vulkan` | Device creation fails (every newer backend, or the listed ones), which exercises the renderer fallback |

## Render features (settings per graphics API)

Rule: a visual feature the engine adds on top of the shipped renderer works on every render API according to what that API can do, and its setting in Options, Video exists only where the running API supports it. Such a feature is registered once in `src/moho/render/RenderFeatures.{h,cpp}` (`render::RegisterFeature`) with its title, tip, console variable, levels (states), default, whether it needs a restart, and for each API (D3D9, D3D10, D3D11, D3D12, Vulkan) whether it is supported, why not, the highest level and the default on that API:

- `data/fafengine/lua/options/optionslogic.lua` (a hook appended to the game's `/lua/options/optionslogic.lua`) builds one Video entry per supported feature when the options data is asked for after the device exists (the options module can load earlier, while the Graphics API option is read, so the entries are synced once per API), after the Graphics API entry. The entry's setter runs the feature's console variable with the level; the profile stores the key of the chosen state.
- The Lua global `GetRenderFeatures()` returns `{ api, features = { { key, title, tip, console, default, restart, states } }, unsupported = { { key, title, reason } } }` for the running API (`api == ''` before the device exists).
- The engine asks `render::FeatureLevel(key, api)` for the level the player chose (the profile option, else the API's default) and calls `render::ApplyStartupSettings()` once after the device is created: a feature's `apply` callback receives the level.
- Changing the Graphics API takes a restart; the list is built for the new API after it.

The registry lives next to the Lua blocks of `data/fafengine/lua/options/options.lua` (shadow cascades, ray-traced shadows, ambient occlusion, Water Quality, ...), which show their entry whenever their console command exists. The two do not clash: a feature whose key is already an option of the tab is left out by `optionslogic.lua`, so each option shows once and a profile that stores the key keeps working. A new engine feature that is hardware dependent goes through the registry; the existing Lua blocks stay as they are.

Registered features:

A state can carry the `value` sent to the console variable (default: the level index), a feature can name the entry it is listed `after`, and `numericKeys` makes the state keys numbers, as options that existed before the registry stored them. `src/moho/render/ImageQualityFeatures.cpp` registers the image-quality entries that way (`fxaa_on`, `sharpen_level`, `grade_on`, `bloom_wide_level`, `texture_anisotropy`, `render_scale`), keeping the option keys and number keys of the Lua blocks they replaced, so a saved profile selects the same state. ## Image quality: anti-aliasing, sharpening, grade, texture filtering, render scale

All of it is render only (nothing reads or writes sim state) and honours `FAF_NO_RENDER_ADDITIONS=1` where it is a post pass.

- **Post pipeline.** `WRenViewport::RenderWorldViewPostEffects` runs once per world view, before the view's overlay pass: the head is copied into the view's refraction target and drawn back through the anti-aliasing (`FxaaRenderer`, or `SmaaRenderer` for `ren_Fxaa 2`) and then `PostRenderer` (sharpening `ren_Sharpen` and the grade `ren_Grade`, one pass), each inside the view's viewport and colour only. Strategic icons, range rings, the cartographic views and the interface stay pixel-exact. The programs use the GPU-driven model (`GpuDriven.h`), so one HLSL source serves Direct3D 11, 12 and Vulkan; `GpuBindings::targets` (a colour target read as a texture in t4..t5) is implemented by all three. `ren_Fxaa` is 0 off, 1 FXAA, 2 SMAA 1x.
- **SMAA** is a lightweight form (`SmaaShader.h`): edge detection, blend weights from a closed-form coverage (no area or search textures), neighbourhood blending; no diagonal search and no corner rounding. Its two working targets are the size of the head copy; a view smaller than the head clears them first (the weight search reads past the view's rectangle).
- **Render scale** (`ren_RenderScale`, upstream's float 0.5 to 1, the share of the view the world is drawn at; the option keys 100, 85, 75, 67, 50 are upstream's). With temporal anti-aliasing running (`ren_Taa`, Direct3D 12 and Vulkan) its resolve rebuilds the full view from the smaller picture. Everywhere else (`ren_Taa` off, Direct3D 11) `moho/render/RenderScale.{h,cpp}` and `gpg/gal/RenderScalePass.{h,cpp}` do it spatially: `WRenViewport::Render` swaps the head's colour and depth lanes and the viewport's frame-copy and normal targets for smaller ones for the world loop. Each view is upscaled into the back buffer when its world is done, and the post effects of that view then run on the upscaled image at the window's size, followed by the overlay: the order is world, upscale, anti-aliasing and sharpening, overlay. `ren_RenderScaleSharpness` is taken as 0 while `ren_Sharpen` is above 0, so the image is sharpened once. Range rings widen by 1 / scale so they stay lines.
- **Post effects verified 2026-11-12** (`fix/postshadow`, RX 7900 XTX, `adaptive_acid_lakes`, game paused, frames matched to their setting by the marker the test camera draws, not by capture order). *Sharpening:* the frame difference to Off at `ren_Sharpen` 0.5 and 1 is 3.08 and 6.12 levels on Direct3D 12 and Vulkan (3.10 and 6.16 on Direct3D 11), repeated in the order 0, 0.5, 1, 0, 1, 0.5, 0 with identical values: monotonic on all three. An earlier Vulkan capture that read 7.2 for 0 to 0.5 and 3.3 for 0 to 1 was a capture artifact: the first frame after a console change still shows the previous state (and the dump counted frames by file number, which runs ahead of the step on some APIs); no state is left unset by the pass. *Anti-aliasing on thin lines* (antenna rods and a radar mast, crops, same frame): the edge energy (mean absolute neighbour difference) kept against Off is 83 % with FXAA and 94 % with SMAA on the rods, 85 % and 93 % over the view, on Direct3D 12, Vulkan and Direct3D 11 (Direct3D 11: 82 / 94 and 87 / 94 %). *Cost* (`FAF_GPU_PROFILE`, per pass GPU ms, 1600x900, three runs each, other games running at the same time, so the whole-frame GPU time moved by +-1 ms between runs and is not quoted; the pass scopes include the head copy): `Fxaa` 0.04 to 0.08 (Direct3D 12), 0.06 to 0.08 (Vulkan), 0.03 to 0.05 (Direct3D 11); `Smaa` 0.06 to 0.10, 0.06 to 0.07, 0.03 to 0.05; `Post` (sharpening and grade) 0.03 to 0.05, 0.03 to 0.04, 0.014 to 0.02; with SMAA and Post together the two add. - **Texture filtering** (`ren_TextureAnisotropy`): one rule (`effects::TakesTextureAnisotropy`: trilinear, wrapping in both directions, texture not named `*lookup*`) on all three APIs. ## Large particles in a lower-resolution target

The explosions of the game are a few hundred quads of 100,000 pixels and more drawn over each other with blending: 100 and more screens of overdraw, which costs blend and fill bandwidth and nothing else. Quads of `ren_ParticleLowResSize` (320) pixels and more are drawn into a half (or quarter) resolution target and composited onto the scene; everything smaller is drawn at full resolution.

- **Where:** `src/moho/particles/ParticleLowRes.{h,cpp}` (runtime), `ParticleEffectPatch.{h,cpp}` (source patch of `particle.fx`), hooks in `CWorldParticles::RenderEffects`, `ParticleRenderBuckets.cpp` (`PrepareParticleBucket`, `DrawParticleBucket`, the large-quad estimate) and `CD3DEffect::InitEffectFromFile` (the patch, cached as `particle.lowres.<engine version>`). The effect is patched only while Soft Particles is on or Large Particle Quality is on with a viewport that can take the path (`particlelowres::PatchWanted`); `particlelowres::ApplyLive`, called at the start of every frame, builds it again with or without the patch when that changes (a resize to or from a viewport of `ren_ParticleLowResMinViewport` Mpix, an option switched), and with both options off the effect, its shaders and its cost are upstream's. If the file does not look as expected, or the patched effect does not build, the original is used and the log says why.
- **Shader:** `WorldVS` and `WorldVSAlign` collapse the quads of the other size class when `LRParams.x` is not 0, so one instanced draw of a bucket can be issued twice from the same data. Every ADD, ALPHABLEND and PREMODALPHA world-particle technique gets a `<name>_LR` twin that accumulates (colour S, coverage A) into the low-resolution target, depth tested by the hardware against a downsample of the scene depth, in drawing order: an "over" layer does S = c*a + S*(1-a), A = a + A*(1-a), an ADD layer S += c*a. Any mix composes exactly (scene' = S + scene*(1-A)) up to the 8 bit clamping. `LRDownsample2/4` and `LRComposite` (depth-aware upsample) are full-screen techniques of the same patch.
- **Runtime:** per bucket (in the buckets' own order) the large quads are drawn into a cleared accumulation target, composited over the rectangle of those quads (`LRRect`), then the small quads of the same bucket are drawn at full resolution; the next bucket follows. (One composite per run of buckets, with all small quads after it, changed the draw order between buckets and made the picture 1.8 levels brighter in green and 3.9 in blue on Direct3D 12 and Vulkan; see the 2026-11-12 verification below.) MODULATE*, REFRACT and TLight buckets are not touched and end a run. A CPU copy of each uploaded particle's vertex shader inputs, kept beside its pooled buffer, estimates which quads are large and how many pixels they cover; a bucket takes the path only when it holds `ren_ParticleLowResMinMpix` (150) million pixels of large quads, covers its rectangle `ren_ParticleLowResMinOverdraw` (14) times over, and the viewport has `ren_ParticleLowResMinViewport` (5) Mpix; everything else, and frames without a big explosion, take the old path unchanged.
- **Depth:** the scene depth stays a depth output; a copy made once per `RenderEffects` call (`Device::CopyDepthStencil`) is sampled through `EffectVariable::SetDepthStencil`.
- **Setting:** Options > Video > Large Particle Quality (Full / Half / Quarter), `ren_ParticleLowRes` 0 / 1 / 2, `ren_ParticleLowResSize`, `ren_ParticleLowResMinMpix`, `ren_ParticleLowResMinOverdraw`, `ren_ParticleLowResMinViewport`, `/noparticlelowres`; `FAF_NO_RENDER_ADDITIONS=1` turns it off too. The passes show up as `LRDepth`, `LRAccum` and `LRComposite` in `FAF_GPU_PROFILE`.
- **Host test:** `faf_particle_tests` (the patch on a minimal source, and on the real `particle.fx` when `FAF_STOCK_FX_DIR` names a folder with it).

**Re-tuning the gate for another GPU, and the order inside one bucket (2026-11-12, `fix/left`).** The three thresholds were tuned on one card (RX 7900 XTX), so they are starting values. To re-tune without rebuilding, set them with the environment variables or `/con` (the table in SWITCHES.md) and compare the pass cost with the path forced on and off on a paused frame (one nuke, camera zooms 14 / 22 / 45 / 90, the resolutions the card is used at; nothing else may run on the machine, the timings move by a third of a millisecond with another game running):
1. `FAF_GPU_PROFILE=300`, `sc_FrameTimeClamp 0`, `ren_FpsLimit 0`. Read the `EffParticles` GPU milliseconds with `ren_ParticleLowRes 0` (Full), then 1 (Half) and 2 (Quarter) with `ren_ParticleLowResMinMpix 0`, `ren_ParticleLowResMinOverdraw 0` and `ren_ParticleLowResMinViewport 0`, so that the path runs whenever there is a large quad.
2. Two numbers come out of that table. The fill price `f`: Full's cost divided by the large-quad pixels (the estimate; on the RX 7900 XTX about 0.003 ms per million pixels). The fixed price `c0`: what Half costs on a frame whose large quads are few (`LRDepth` + `LRAccum` + `LRComposite`, 0.4 to 0.6 ms) plus 0.015 ms per million pixels of the composited rectangle.
3. `ren_ParticleLowResMinMpix` is `c0 / f` (here 0.5 / 0.003, about 150): below that many million pixels of large quads a bucket does not pay for its extra passes. `ren_ParticleLowResMinOverdraw` is the break-even overdraw (the rectangle price over the fill price, here 0.015 / 0.003 = 5) with a margin (14 ships). `ren_ParticleLowResMinViewport` is the smallest viewport at which the biggest explosion you care about gains at all (5 million pixels here); a card with slower blending or less cache (higher `f`) gains earlier, so all three go down; a card on which Half never wins at 5 million pixels wants `ren_ParticleLowRes 0` as its default and a large `ren_ParticleLowResMinViewport`.
4. Check the picture, not only the time (below): the thresholds change which buckets are drawn low, and a wrong estimate costs time, never pixels.

*Order inside one bucket (left as it is).* A bucket's pooled buffers draw large quads into the accumulation target, composite, then draw the small quads of the same buffers at full resolution, so within one buffer every small quad comes above every large one whatever their spawn order. Putting them back in order would take one composite per change of size class along the buffer's instances. The class of a quad is decided exactly only in the vertex shader; the CPU copy that the gate keeps is an estimate (on purpose: a wrong estimate costs time, never pixels), and splitting draws by it would turn an estimate error into an order error you can see. Doing it exactly needs a GPU-side classification pass or a sort of the instances by class (changing the draw order of every other quad), and each composite costs 0.26 to 0.42 ms at 3840x2160. The residual it leaves is below one level (-0.2 to -0.3 per channel on smoke wisps on all three APIs, below), so it is not worth that.

*Smoke-only check (same paused frame, 1600x900, forced path with `ren_ParticleLowResSize` 40 so that the smoke wisps of a nuke's shock wave count as large, no fireball in the frame, game paused at 42 s, target 150,150, camera zoom 45; mean signed RGB difference of Half and Quarter against Full over the 1600 x 740 world area; the full-resolution frame against itself in the same run as the noise floor).* Half against Full: Direct3D 11 (-0.31 -0.22 -0.21; mean largest-channel difference 1.21, 0.02 % of the pixels above 24), Direct3D 12 (-0.33 -0.24 -0.25; 1.20, 0.09 %), Vulkan (-0.30 -0.23 -0.19; 1.19, 0.02 %); Quarter against Full: (-0.55 -0.41 -0.34; 1.70, 0.49 %), (-0.56 -0.43 -0.42; 1.67, 0.48 %), (-0.52 -0.42 -0.33; 1.64, 0.42 %); Quarter against Half about -0.2 in each channel. Full against Full again: 0.00 on Direct3D 11 and Vulkan, +0.02 on Direct3D 12 (0.07 % of the pixels above 24: animated effects). The residual is the same on all three APIs, Direct3D 11 included, and it is a slight darkening of the soft wisps in every channel: that points to the 8 bit accumulation target rounding the low coverage of the wisps (`c * a` truncated per layer) rather than to the order of the quads, which would not be API specific and would not be of one sign. The two were not told apart (a half float accumulation target would settle it, at twice the bandwidth of that pass); the figure is below one level at the mean, and the Quarter frame's 0.4 to 0.5 % of pixels above 24 are the resolution of its soft edges.

**Portability review, NVIDIA / Intel (read from the code 2026-11-12, nothing of it run on such a GPU):**
- *Depth format.* The scene depth copy and the low-resolution depth are sampled depth targets: D24S8 where the device has it (D3D12; Vulkan asks `vkGetPhysicalDeviceFormatProperties`, D24S8 on NVIDIA / Intel, D32S8 on AMD); `CopyDepthStencil` needs identical formats and sizes and turns the path off (log line) when it cannot copy. The composite's depth weights compare view distances worked out from the stored depth (`LRViewZ`), which D24 holds with less precision than D32 far away; the tolerance (1.5 % of the distance) was tuned on AMD's D32S8 in Vulkan and on D24S8 in D3D12, both fine.
- *Implicit derivatives after `discard`.* The composite read its depth texture with `tex2D` after a `discard`; on NVIDIA / Intel the surviving invocations are not a full quad and the implicit level is undefined. Fixed (explicit `tex2Dlod`). Every other particle texture read is unconditional or already `tex2Dlod`.
- *Depth export.* `LRDownsample2/4` write the depth from the pixel shader with colour writes masked (disables early depth tests, full-screen quad at low resolution only); legal everywhere, slower on old Intel parts.
- *8 bit accumulation.* The accumulation target is B8G8R8A8: blending on 8 bit rounds differently per vendor (the Direct3D 12 / Vulkan residual of -0.3 / -0.5 in green / blue against Full may change sign elsewhere); a half float target would remove the question at twice the bandwidth of that pass.
- *Alpha blending with colour factors* (the Direct3D 9 rule the effect translation applies): the alpha factors are mapped to alpha forms (`AlphaFactor`); `*_COLOR` factors are not legal for alpha on Direct3D 12 and Vulkan, so a missed mapping would be a validation error there.
- *NaN positions.* The vertex shaders return a zero position for culled quads (no NaN), but the flash pull `normalize(camera - position)` of soft particles is NaN for a particle exactly at the camera; NaN positions are dropped by the rasteriser on the vendors known, not guaranteed.
- *Barriers.* The low-resolution depth is a depth attachment in `LRAccum` and a sampled texture in `LRComposite`, the scene depth is never sampled directly; these are different passes with transitions in the backends, not simultaneous read-only/attachment use.

## Soft particles

Smoke, fire and explosion quads are flat cards: where one cuts into the ground, a unit or the water it leaves a hard line. Soft particles fade the quad's alpha by the distance between its own depth and the scene depth behind it, so the line becomes a gradient. Option: Options > Video > Soft Particles (Off / Low / High, default Low), console variable `ren_SoftParticles` 0 / 1 / 2.

- **Shader** (the same load-time patch of `particle.fx`): the ADD, ALPHABLEND and PREMODALPHA world-particle techniques (and the `_LR` twins) use `WorldPSSoft` / `WorldPSSoftPremod` in place of `WorldPS`. They scale the alpha (the whole colour for PREMODALPHA, whose alpha is in the colour) by a smoothstep of (scene view depth - fragment view depth) / `SoftParams.x`. The flat techniques (`TRampFlat`, `TRampAnimateFlat`) lie on the ground by design and stay hard-edged.
- **Distance per level:** Low 1 world unit, High 3, times `ren_SoftParticleScale`.
- **Depth:** the same sampled copy of the scene depth the low-resolution path uses, taken lazily just before the first eligible bucket is drawn (`particlelowres::EnsureSoftDepth`) and kept bound until the end of the call. The `_LR` twins look the copy up at the full-resolution pixel their low-resolution pixel is centred on.
- **Cost:** one depth lookup and a few ALU operations per particle pixel, and one copy of the depth per frame that draws particles.

**Verified 2026-11-12** (same scene and machine as above, 1600x900, Off against High on the paused nuke frame, mean largest-channel difference 0-255): Direct3D 12 2.0 (1.8 % of the pixels differ by more than 24), Direct3D 11 2.0 (1.9 %), Vulkan 2.1 (3.2 %); two frames of one setting differ by 0.01 to 0.06. The difference lies where the fireball's quads meet the ground: the stair-step bands of the Off frame become a smooth gradient on all three APIs. Cost (Direct3D 12, 1600x900): the depth copy `SoftDepth` 0.010 to 0.025 ms, `EffParticles` about +0.03 to +0.05 ms (0.436 to 0.482 ms). Not verified: smoke over water with a unit in it (a lake scene), a Low against High comparison by eye, other GPUs.


## Frame rate limit

A cap on the frames per second, for power, heat and fan noise, and against the coil whine some graphics cards make at a few hundred frames per second. It is the main loop's own mechanism: `CScApp::Main` returns to the message pump with `WIN_SetWakeupTimer` for the rest of the frame when less than the shortest frame time has passed, and `sc_FrameTimeCarry` gives a late wake-up (the timer sleeps in whole milliseconds) back to the next frame, at most half a frame, so the rate holds on average. The pump keeps running while the loop waits, so input and window messages are never held for a frame.

- **Where:** `src/moho/render/FrameLimiter.{h,cpp}` decides the shortest frame: `FrameLimiterShortestFrameMs()` is 1000 / the limit while a limit is set, else `sc_FrameTimeClamp` (4 ms, 250 FPS). A limit above 250 FPS therefore lets the loop run faster than `sc_FrameTimeClamp` does.
- **Setting:** Options > Video > Frame Rate Limit (Off, 30, 60, 90, 120, 144, 165, 200, 240; Off is the 250 FPS clamp), `ren_FpsLimit` (the level), `ren_MaxFps N` (any value, wins over the level) or `/maxfps N` on the command line.
- **Vsync:** with vsync on, the display's refresh rate paces the frames too; a limit that divides the refresh rate keeps them evenly spaced, and a limit above it changes nothing.
- **Needs** the 1 ms timer resolution the movie manager raises at start (see `/hrtimer` in [SWITCHES.md](SWITCHES.md)); without it a frame waits a whole system tick.

**Verified 2026-11-12** (RX 7900 XTX, windowed 1600x900, a static scene, a 240 Hz display with vsync on, no frame dumps; frame times are those of `WaitFrames(1)` in the interface thread, 8 s per setting, in milliseconds; "Off" is the 250 FPS clamp held back to 240 by vsync):

The rate holds to the millisecond on all three APIs; the 1 ms wake-up granularity shows as a spread of 0.2 to 0.3 ms (1st to 99th percentile within +-0.6 ms of the mean at 60), so a finer wait than the carry is not needed. Not the limiter, nothing changed; to separate the driver from the machine it needs a run with nothing else on the GPU. ## Stratum mask resolution

The map file stores the stratum masks (the two textures that blend the eight terrain layers) at whatever size the mapper saved them. `CWldTerrainRes::Finalize` used to copy both into new dynamic sheets of exactly half the map's size (`(heightfield width - 1) / 2`), and that copy is a resample on every API, so a mask saved at a higher resolution was reduced to that preset: a 40 km map (2048 cells) kept 1024 of its 2048, an 81 km map 2048 of 4096.

- **Now** (`src/moho/terrain/StratumMaskSize.h`, per axis): a mask keeps the size it was saved with, but never less than half the map's size (a coarser mask is raised to it, as before) and never more than `max(2048, 2 x map cells)`, with the ceiling `ren_StratumMaskMax` (8192). So 2048 is allowed on any map (10 km, 20 km), 4096 only on a 40 km map or larger, and 8192 only on an 81 km map; the extra resolution is memory (an 8192 mask is 256 MB, two of them 512 MB) that a smaller map cannot use. The rules are `static_assert`s in the header and a host test (`faf_stratum_mask_tests`). `mStratumMaskWidth` / `Height` follow mask 0. The log has one line per map: `Terrain: stratum masks WxH and WxH (saved in the map as ...; half the map is ..., the most ...)`.
- **`ren_StratumMaskMax 0`** gives back the shipped sizes (half the map). The value is read as the terrain finishes loading, so it applies to the next map.
- **`FAF_STRATUM_MASK_TEST=1`** replaces the loaded masks with a fine test pattern before the copy (the loaded sheets are not lockable, so a lockable sheet of the same size takes their place as the copy's source): 64-texel tiles, each with one-texel vertical stripes, one-texel horizontal stripes, a four-texel checker or a one-texel diagonal hatch. It stands in for a mapper's detailed mask and shows the resolution the copy keeps.
- **Not changed:** the water map and the water masks stay at half the map's size, and the editing calls (`UpdateStratumMask`, `GetStratumMask`) take their rectangle from the mask 0 size.

**Verified 2026-11-12** (windowed 1600x900, `MKLOUD1`, an 81 km map whose masks are saved at 4096 x 4096, `FAF_STRATUM_MASK_TEST=1`, camera at four zoom levels over the same ground): `ren_StratumMaskMax 0` logs `stratum masks 2048x2048 and 2048x2048 (saved in the map as 4096x4096 ...)` and the one-texel pattern is averaged away; the default logs `4096x4096 and 4096x4096`, the map loads and renders on Direct3D 11, 12 and Vulkan, and the stripes, checker and hatch are in the picture on all three. Direct3D 12, the two builds of the setting against each other: mean largest-channel difference 10 to 14 levels, 13 to 23 % of the pixels over 24, at the closer zooms. Not verified: an 8192 mask (no such map at hand), a 10 km or 20 km map with a 2048 mask in the game (the size rule is covered by the host test only), video memory and load time at 4096 (two 4096 masks are 128 MB of sheets), the water map (unchanged).
