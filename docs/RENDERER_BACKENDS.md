# Renderer backends

The engine draws through `gpg::gal`, the GPG abstraction layer. The shipped binary had Direct3D 9 (default) and Direct3D 10 (`/D3D10`); this fork adds Direct3D 11, Direct3D 12 and Vulkan, and by default takes the newest one that starts.

*Snapshot: 24/10/2026.*

| Switch | Backend | Effects | Code |
|---|---|---|---|
| `/d3d9` | Direct3D 9 | D3DX9 effect framework | `src/gpg/gal/backends/d3d9` |
| `/D3D10` | Direct3D 10, as shipped | D3DX10 | `src/gpg/gal/backends/d3d10` |
| `/d3d11` | Direct3D 11 | Effects 11 (FX11), `fx_5_0` | `src/gpg/gal/backends/d3d11` |
| `/d3d12` | Direct3D 12 | FAF effect layer, DXIL via DXC | `src/gpg/gal/backends/d3d12` |
| `/vulkan` | Vulkan 1.3 | FAF effect layer, SPIR-V via DXC | `src/gpg/gal/backends/vulkan` |

## Choosing the renderer

Players pick it under Options, Video, **Graphics API**: Automatic, Direct3D 9, Direct3D 11, Direct3D 12 or Vulkan. The choice is stored as the option `graphics_api` (`auto`, `d3d9`, `d3d11`, `d3d12`, `vulkan`; default `auto`) in the profile's options, like `vsync`.

| Choice | Renderers tried, in order |
|---|---|
| `auto`, unset, unknown value (x64) | Direct3D 12, Vulkan, Direct3D 11, Direct3D 9 |
| `auto`, unset, unknown value (x86) | Direct3D 11, Vulkan, Direct3D 12, Direct3D 9 (see [Known issues](#known-issues)) |
| `d3d12` / `vulkan` / `d3d11` | That one, then Direct3D 9 |
| `d3d9` | Direct3D 9 |

- **Command line wins:** `/d3d9`, `/d3d11`, `/d3d12`, `/vulkan` override the option the same way; `/D3D10` is tried alone.
- **Fallback:** a renderer counts once its device is created and set up. One that cannot start is logged with the reason, and the next is tried with the same window settings (`CScApp::CreateDevice`, order from `RendererAttemptOrder`).
- **Restart needed:** the option is read once at startup (`OPTIONS_GetString`), so changing it raises the options screen's standard "requires a restart" dialog (`restart = true`), whose OK saves and exits. Switching renderers without a restart is not supported: the existing device rebind (`CD3DDevice::InitContext`, used for resolution, vsync and anti-aliasing changes and for a lost device) resets the *same* gal device, recreating only what a Direct3D 9 reset loses and keeping file textures, static buffers and compiled effects.
- **Window title** names the renderer in use (`Forged Alliance [Vulkan] ...`; no tag for Direct3D 9). `/title <label>` appends a label, to tell side-by-side test windows apart.
- **Testing the chain:** `FAF_GAL_FAIL_SETUP=1` fails every newer backend; a list such as `d3d12,vulkan` fails only those (Direct3D 12 and Vulkan read the list, Direct3D 11 only `1`).

The log shows each step:

```
graphics_api option: auto
renderer: trying Direct3D 12
GAL Exception: ...                      (the reason it failed)
Direct3D 12 is unavailable; falling back to Vulkan
renderer: trying Vulkan
Vulkan: ready (...)
```

### Where the option comes from

The options entry comes from the engine's own Lua, never from edits to FAF's gamedata:

- **Source:** `data/fafengine/` holds engine-owned scripts that extend gamedata scripts. The build copies it next to the executable (`src/CMakeLists.txt`), and `build.ps1` copies it into the run folder.
- **Mount:** at startup the engine mounts `<exe folder>/fafengine` at `/fafengine` and registers it as a hook directory, after the init file's own `path` and `hook` entries (`AppendEngineHookFolder` in `src/moho/misc/StartupHelpers.cpp`). The engine does this itself because the init files (`init_faf.lua` and the rest) belong to the FAF client.
- **Hook:** a hook file is appended to the gamedata file of the same path, so `fafengine/lua/options/options.lua` runs at the end of `/lua/options/options.lua` and inserts the entry after Vertical Sync. The log says `engine hooks: ... mounted at /fafengine` and `Hooked /lua/options/options.lua with /fafengine/lua/options/options.lua`.

## Effects: one source, translated at load time

The game's `.fx` files are user data. They are never copied into this repository; the ports below run on them at load time.

1. **Preprocess** with the Direct3D 10 macros (`technique` becomes `technique10`, `vs_3_0` becomes `vs_4_0`, and so on) and `d3d10states.compat` prepended (`CD3DEffectTechnique`), using `D3DPreprocess` from d3dcompiler_47.
2. **Override layer** (`backends/d3d11/EffectSourceD3D11.cpp`) rewrites the D3D9-isms the effects still have: D3D9 pass states become state objects, `sampler1D` and `tex1D` become 2D, shader inputs are re-linked, and the D3D9 fixed-function vertex shader is emulated for pre-transformed vertices. Fixes go here, never into the gamedata.
3. **Direct3D 11** compiles the result as `fx_5_0` and loads it into Effects 11.
4. **Direct3D 12 and Vulkan** hand it to the FAF effect layer (`src/gpg/gal/effects`):
   - `EffectDescription`: techniques, passes, annotations (constant expressions folded), blend, depth-stencil and rasterizer states, sampler states, and parameters with their defaults.
   - `ModernHlsl`: plain HLSL. Techniques and states are removed; the FX9 sampler model becomes `Texture2D`/`TextureCube`/`Texture3D` plus `SamplerState` on fixed registers; parameters a function writes get local copies; stage boundaries get `SV_` semantics. One wrapper entry point per (stage, function, compile-time arguments). The predicted `$Globals` layout matches DXC's reflection for every entry point.
   - `ShaderCompiler`: DXC (`dxcompiler.dll`), shader model 6.0, `-HV 2018 -Zpr`, producing DXIL or SPIR-V (`-fvk-use-dx-layout`).
   - `EffectParameters`: the `$Globals` image, written with Direct3D 9 / Effects 11 setter semantics and snapshotted when a pass begins.
   - `EffectRuntime`: the gal `Effect`/`EffectTechnique`/`EffectVariable` shared by both backends. Vulkan links stages by location while DXC numbers each shader's interface on its own, so `SpirvReflect` matches vertex inputs and the vertex-to-pixel interface by HLSL semantic. Shaders compile on first use and are cached in `%LOCALAPPDATA%\FAForever\ShaderCache` (or `FAF_SHADER_CACHE_DIR`).

**Why DXC:** Slang and DXC were both tried on the real effects. Both reject raw FX9 texture/sampler syntax, so a modernisation pass is needed either way. After that pass DXC compiled all 339 entry points of the 11 effects to DXIL and to SPIR-V; Slang failed most entries of `water2`, `particle` and `terrain`, mostly on implicit vector truncation and writes to globals, which FXC-era HLSL relies on.

### D3D9 behaviour restored

The D3D10 state packs lost some of what D3D9 did; the newer backends restore it:

- **Clear** covers the viewport (clipped to the targets), not the whole target.
- **Viewport reset:** binding a different colour target resets the viewport to the whole target (D3D9's `SetRenderTarget`). The engine clears the shadow map before it sets a viewport; without the reset, part of it keeps stale depth.
- **Depth clipping** is always on (`d3d10states.compat` turns it off, which lets shadow casters outside the light's range clamp onto the map).
- **Depth bias:** the compat file's fractional `DepthBias` values are D3D9 depth-range fractions, converted to 24-bit depth steps (fxc truncates them to 0, and the ground decals then z-fight the terrain).
- **Alpha blending:** the alpha channel blends with the colour factors (D3D9 had separate alpha blending off). The compat file sets `SrcBlendAlpha = ONE`, `DestBlendAlpha = ZERO` on every state, which overwrites the frame's alpha, and that alpha is the glow mask: the commander's warp-in light then lit its whole quad as a hard-edged rectangle.
- **Pixel centres:** Direct3D 9 puts them on integer coordinates, Direct3D 10+ and Vulkan on halves, and the engine draws for D3D9 (the UI projection `CD3DPrimBatcher::SetToViewport` shifts quads by -0.5 pixel). Every backend therefore moves the native viewport origin by +0.5 pixel (`Direct3D9PixelCentreShift`); without it UI text sampled between texels and looked doubled. The fixed-function emulation's `faf_ViewportSize` takes the same shift.
- **Alpha test:** effects still set `AlphaTestEnable`, `AlphaFunc` and `AlphaRef` in their passes, inside `#ifndef DIRECT3D10`, and FAF's water shader relies on it (`HighFidelityPS` returns the land mask in alpha, and `NotEqual 0` discards it). The effect layer reads these states from the original source (`ApplyDirect3D9PassStates`) and the pixel entry discards as D3D9 did, on the 8-bit alpha. The effects' own `AlphaTestD3D10` helper, which D3D9 never ran, is emptied. Without the alpha test the water drew over the land as grey polygons when zoomed out.
- **Technique begin state** culls nothing, as Direct3D 9's does (`PipelineStateD3D9::BeginTechnique`); the D3D10 pack culls back faces. A pass that sets no cull mode draws with it: the low and medium fidelity water passes are such passes, and with culling their map-sized quad was dropped, which left the seabed showing untinted, dark, and without wave crests.
- **Shader math** as shader model 2/3 compiled it: `sqrt`/`rsqrt` of `|x|`, and `pow` of `|x|` (sign kept for odd integer exponents). Shader model 6 returns NaN for a negative operand, and a NaN blended into a target stores zero.
- **Missing vertex inputs** (ones a vertex format lacks) read as zero.
- **Feedback:** a pass that samples the target it draws into reads zero, as on D3D10/11.

## GPU-driven paths

The GPU-driven renderers (strategic icons with GPU classification, fog of war, instance streams) use the small binding model in `src/gpg/gal/GpuDriven.h`: one constant block, four read buffers, two textures, two write buffers and one sampler. Every newer backend implements all of it.

| | Programs | Binding |
|---|---|---|
| Direct3D 11 | d3dcompiler `vs/ps/cs_5_0` | Registers b0, t0..t5, u0..u1, s0 directly |
| Direct3D 12 | DXC `vs/ps/cs_6_0` (`ShaderCompiler::CompileRaw`) | One root signature per sampler kind: root CBV b0, SRV table t0..t5, UAV table u0..u1, static sampler s0; `ExecuteIndirect` for indirect draws (`d3d12/GpuDrivenD3D12.cpp`) |
| Vulkan | DXC SPIR-V with `-fvk-b-shift 0 -fvk-t-shift 1 -fvk-u-shift 7 -fvk-s-shift 9` | One descriptor set, bindings 0..9; `vkCmdDrawIndirect`; compute outside the rendering scope (`vulkan/GpuDrivenVulkan.cpp`) |

GPU timestamps feed `RenderProfiler` (`FAF_GPU_PROFILE=<frames>`). `FAF_ICON_GPU_CHECK=<n>` compares every n-th GPU-classified icon frame with the CPU path, record by record.

### Turning the paths on

Each path has a console variable with three values: `-1` (default, auto: on only where the backend reports both the features the path needs and the path's verified bit), `0` (off: the original draw path), `1` (force on wherever the features exist, for testing a backend before it is verified). Two `gal::Device` queries decide it (`src/moho/render/GpuPathSettings.cpp`):

- **`GetGpuDrivenFeatures()`**: what the backend can do (`GpuDrivenFeature` bits: vertex pulling, compute, indirect draws, timestamps, buffer copy).
- **`GetGpuDrivenVerified()`**: the `GpuDrivenPath` bits the backend has passed parity on. The base `Device` returns 0, so a backend that does not override it draws everything the original way under auto.

| Console variable | Path bit | Needs |
|---|---|---|
| `ren_GpuIcons` | `kGpuPathStrategicIcons` | Vertex pulling |
| `ren_GpuIconClassify` | `kGpuPathIconClassify` | Vertex pulling, compute, indirect draws (also needs `ui_IconRecords`) |
| `ren_GpuFog` | `kGpuPathFogOfWar` | Vertex pulling |
| `ren_GpuSelectBrackets` | `kGpuPathSelectBrackets` | Vertex pulling |
| `ren_ParticleBatch` | `kGpuPathParticleBatch` | Buffer copy (`Device::CopyVertexBufferRegion` on the GPU) |
| `ren_GpuProjectileIcons` | `kGpuPathProjectileIcons` | Vertex pulling |
| `ren_GpuShapes` | `kGpuPathWorldShapes` | Vertex pulling |

- **Direct3D 9** reports no features, so every path is off there whatever its variable says.
- **Direct3D 11, 12 and Vulkan** report all features and every verified bit except `kGpuPathParticleBatch`, which stays out until a paused screenshot A/B of `ren_ParticleBatch` is clean at several zooms (one showed extra particle specks with it on).
- **Verifying a path:** a backend turns a path on by default by adding its bit to `GetGpuDrivenVerified()` once it passes that path's checks (the self-check readback where one exists, and a same-process screenshot A/B against the variable at 0); no variable or default changes.
- **Log:** the resolved state is logged once at startup and by `ren_Info`, as `GPU-driven paths: ren_GpuIcons=auto:on, ...`.
- `ui_IconRecords` and `ren_CacheFogFootprint` are CPU-side and on by default on every backend. All of these variables are also listed in [Switches](SWITCHES.md).

## Toolchain setup

Configuring the CMake build fetches all three into `dependencies/` (`cmake/FafDependencies.cmake`):

- **FX11 (Direct3D 11):** git submodule `dependencies/FX11`, `microsoft/FX11` at `bec3b8fc`. The engine compiles FX11's sources directly (C++17, two-phase lookup off).
- **DXC (Direct3D 12, Vulkan):** the [DirectXShaderCompiler release](https://github.com/microsoft/DirectXShaderCompiler/releases) v1.9.2609 (`dxc_2026_09_29.zip`, SHA256-pinned), unpacked to `dependencies/dxc`. At run time the game loads `dxcompiler.dll` and `dxil.dll` (the DXIL signer) from its own directory, or from `FAF_DXC_DIR`; copy the DLLs for the right architecture next to the executable.
- **Vulkan headers (Vulkan):** git submodule `dependencies/vulkan`, `KhronosGroup/Vulkan-Headers` at `v1.4.304`. The game loads `vulkan-1.dll` (installed with the GPU driver) at run time and links no import library, so x86 and x64 both build from the headers alone.

### Runtime requirements

Both are optional; without them the game falls back to Direct3D 9.

- **D3DX11:** `/d3d11`, `/d3d12` and `/vulkan` decode textures with D3DX11 (`d3dx11_43.dll`, from the DirectX End-User Runtime of June 2010), as the shipped D3D10 path did with D3DX10. Direct3D 12 and Vulkan run it on a private WARP device (`backends/common/ImageCodec`).
- **Direct3D 12** needs Windows 10 (d3d12.dll is loaded at run time).
- **Vulkan** needs a Vulkan 1.3 driver with dynamic rendering, synchronization2, timeline semaphores, scalar block layout (`$Globals` keeps Direct3D's packing) and BC textures. It runs windowed or borderless only (no exclusive full screen).

## Known issues

- **Direct3D 12 in the 32-bit build, NVIDIA** (seen on a TITAN RTX, driver 32.0.15.7270): after minutes of play the GPU takes an SM MMU fault (`Graphics SM Warp Exception ... MMU Fault`, Xid 13 in the System event log) and the device is removed as hung (`0x887A0006`). It shows on any draw or dispatch (the bloom extract `frame.fx:TCopyGlowingStuff` and `StrategicIconClassify` most often), right after a submission split mid-frame by upload pressure, and is much more frequent with `FAF_GAL_UPLOAD_SUBMIT_KB=1024`. The debug layer, GPU-based validation and anything that slows the CPU hide it; the x64 build of the same code runs the same load cleanly. No application error was found (see the investigation notes in the commit), so `auto` starts the 32-bit build with Direct3D 11. It stays available with `/d3d12` or `graphics_api = d3d12`.
- **Vulkan on NVIDIA:** `PrintWindow(PW_RENDERFULLCONTENT)` on the game window (some capture tools do this) makes `PeekMessage` report a message that `GetMessage` then never returns. The engine's loop (`WIN_AppExecute`, as shipped: `Pending()` then `Dispatch()`) sleeps in `GetMessage` until the next input, so the game stands still until the mouse moves. Any posted message wakes it; the test scripts post `WM_NULL` after each capture.
- **`/D3D10` crashes at startup** on both x86 and x64, as shipped: `DeviceD3D10::SetupDXGIDevice` copies an `AdapterD3D10` without AddRef, so the temporary's destructor releases the adapter and its outputs, which the code then uses after they are freed. It is left as the binary had it.

## Vsync and swap-chain handling

Reports of crashes on vsync changes and presents on NVIDIA and Intel led to a read-through of every swap-chain path. The only GPU available for testing was an AMD RX 7900 XTX, so what follows says what was run and what was only reasoned.

**What changed**

- **`SC_VerticalSync` now applies the value.** The Options > Video toggle runs `SC_VerticalSync <0|1>`, which reset the device from a copy of the current context. The copy still held the old vsync setting, so on every backend the toggle rebuilt the device and left the present interval alone. The command now sets `mVSync` from its argument first (`ResolutionCommands.cpp`).
- **D3D11 and D3D12: a Reset rebuilds only what changed** (`dxgi/DxgiSwapChainPolicy.h`, `PlanReset`). Vsync is only the present interval: when no chain differs (vsync, anti-aliasing, the same resolution set again) the back buffers stay and the Reset only hands back the start-up state. A windowed size change is a `ResizeBuffers`; a window-mode change (the head's full-screen flag, the full-screen size or refresh rate) builds a new chain, because the tearing flag and the display mode are fixed when it is made. A minimised window keeps its chain. The head's full-screen flag and refresh rate are now copied into the device context on a Reset (they were ignored).
- **A failed `ResizeBuffers` no longer throws from `CreateRenderTargets`.** `SwapChain::Reconfigure` retries once after the GPU is drained (D3D12: two submissions and a fence wait; D3D11: `ClearState` + `Flush`), then creates a new chain; a full-screen chain that cannot be made falls back to a windowed one, and as a last resort the previous chain is built again. Only when none can be made does the Reset throw (the engine's `InitContext` catches it as before). A removed device is passed to the existing recovery (D3D12: reason, DRED breadcrumbs, `gpg::Die`; D3D11: reason, exit).
- **Present results are classified** (`ClassifyPresent`). `DXGI_STATUS_OCCLUDED` is a success code: nothing waits, and the log says once when the window is occluded and when it is visible again. `DXGI_ERROR_MODE_CHANGE_IN_PROGRESS` and `WAS_STILL_DRAWING` drop the frame. `DXGI_ERROR_INVALID_CALL` with the tearing flag is retried once without it and tearing is then off for that chain; without the flag the chain is rebuilt through the engine's own Reset (`TestCooperativeLevel` answers 1, `CD3DDevice::Paint` rebinds the context), three times at most, then it throws as before. Device removed / reset / hung / driver error end in the existing recovery.
- **Chain creation drops optional flags before giving up.** A driver that refuses ALLOW_TEARING (or the frame-latency object) gets the same model without it before the next model is tried. The tearing flag stays consistent: it is set only for a windowed chain, `ResizeBuffers` passes the creation flags, the present flag is used only without vsync and outside exclusive full screen (asked from DXGI, because DXGI can leave exclusive mode by itself).
- **Frame latency (D3D11, D3D12), off by default.** `FAF_GAL_FRAME_LATENCY=1..3` makes the chain a `FRAME_LATENCY_WAITABLE_OBJECT` chain with that many frames queued at most (never more than the buffer count) and waits on the object after each present, before the next frame is recorded, for lower input lag with vsync. The wait is skipped while the window is occluded and gives up for good after three timeouts in a row; the object is made again after each `ResizeBuffers`. Without the variable the chain is exactly as before.
- **Vulkan:** a minimised window (surface extent 0 x 0) keeps its swap chain instead of creating one with no area. `VK_ERROR_OUT_OF_DATE_KHR` / `VK_ERROR_SURFACE_LOST_KHR` from acquire or present (and `VK_SUBOPTIMAL_KHR` when the window size no longer matches the chain) ask the engine for a Reset the same way, three times at most; before this an out-of-date chain left every later acquire failing and the window black. A chain that cannot be created is retried without the old chain and, when the surface was lost, on a new surface. Vulkan fixes the present mode (FIFO / mailbox / immediate) when the chain is made, so a vsync change rebuilds the chain (no Reset otherwise); an unchanged chain is not rebuilt.
- **Direct3D 9:** the present interval is a field of `D3DPRESENT_PARAMETERS`, so a vsync change needs `IDirect3DDevice9::Reset` by API design, and there is no flip chain, tearing flag or `ResizeBuffers` to get wrong. The Reset array of present parameters leaked on every call (the binary never freed it); it is freed now. A failed `Reset` is logged with its HRESULT and throws as the binary does.

**Verified on AMD (RX 7900 XTX, `/d3d12debug`, `/d3d11debug`, `/vulkandebug`, windowed 1600 x 900, `adaptive_acid_lakes`)**: on Direct3D 12, 11, Vulkan and 9, Vertical Sync switched with `SC_VerticalSync` from a UI script four times, then 16 times in 4 s, then a maximise/restore pair twice (four `ResizeBuffers` between 1600 x 900 and 2560 x 1351 on D3D11 and D3D12, four swap-chain rebuilds on Vulkan), minimise and restore, and rapid window-size changes; no crash, no debug-layer or validation message about back buffers or swap chains, the vsync-only Resets rebuild nothing on D3D11 and D3D12 (and the log says so). Direct3D 12 also ran with `FAF_GAL_FRAME_LATENCY=2`: the wait is set up at creation and again after every resize, with no timeout. The Vulkan run shows `VK_SUBOPTIMAL_KHR` rebuilds only while the window really had another size than the chain. The pure decisions (`ClassifyPresent`, `PresentFlags`, `PlanReset`, the frame-latency clamp) have host tests: `cmake --build --preset clang-x64-release --target faf_dxgi_tests`, then `build/clang-x64-release/tests/faf_dxgi_tests.exe`.

**Reasoned only (no NVIDIA or Intel hardware)**: the tearing retry after `INVALID_CALL`, the `ResizeBuffers` retry and the chain recreation (nothing failed on AMD), exclusive full screen entered or left through a Reset, the hybrid-GPU present path (an Intel iGPU driving the display from an NVIDIA dGPU), a window moved to an output of another adapter, the occluded-present path, the frame-latency wait on a real NVIDIA / Intel driver, and the Vulkan out-of-date and surface-lost paths. If a crash on those still shows up, the log now names the HRESULT and the step; `FAF_GAL_FRAME_LATENCY` stays unset unless the lower input lag is wanted.

## Render features (settings per graphics API)

Rule: every visual feature the engine adds on top of the shipped renderer works on every render API according to what that API can do, and has a setting in Options, Video that exists only where the running API supports it. A feature is registered once in `src/moho/render/RenderFeatures.{h,cpp}` (`render::RegisterFeature`) with its title, tip, console variable, levels (states), default, whether it needs a restart, and for each API (D3D9, D3D10, D3D11, D3D12, Vulkan) whether it is supported, why not, the highest level and the default on that API. Nothing else is needed for the setting:

- `data/fafengine/lua/options/optionslogic.lua` (a hook appended to the game's `/lua/options/optionslogic.lua`) builds one Video entry per supported feature when the options data is asked for after the device exists (the options module can load earlier, while the Graphics API option is read, so the entries are synced once per API), after the Graphics API entry. The entry's setter runs the feature's console variable with the level; the profile stores the key of the state.
- The Lua global `GetRenderFeatures()` returns `{ api, features = { { key, title, tip, console, default, restart, states } }, unsupported = { { key, title, reason } } }` for the running API (`api == ''` before the device exists).
- The engine asks `render::FeatureLevel(key, api)` for the level the player chose (it reads the profile option, else the API's default) and gets `render::ApplyStartupSettings()` called once after the device is created: a feature's `apply` callback receives the level.
- Changing the Graphics API takes a restart; the list is built for the new API after it.

Registered features:

## Soft particles

Smoke, fire and explosion quads are flat cards: where one cuts into the ground, a unit or the water it leaves a hard line. Soft particles fade the quad's alpha by the distance between its own depth and the scene depth behind it, so the line becomes a gradient. Option: **Options > Video > Soft Particles** (`soft_particles`, Off / Low / High, default Low; console variable `ren_SoftParticles` 0 / 1 / 2, live) on Direct3D 11, 12 and Vulkan; Direct3D 9 runs the shipped ps_2_0 particle shaders as they are and has no depth read there, Direct3D 10 does not start.

- **Shader** (`src/moho/particles/ParticleEffectPatch.cpp`, the same load-time patch of `particle.fx` as Large Particle Quality, no game file changed): the ADD, ALPHABLEND and PREMODALPHA world-particle techniques (and their `_LR` twins of the half-resolution path) use `WorldPSSoft` / `WorldPSSoftPremod` (`WorldPSSoftLR*` for the twins) in place of `WorldPS`. They read the scene depth copy (`LRSceneDepthTexture`), convert both depths to a distance along the view axis and scale the alpha (the whole colour for PREMODALPHA, whose alpha is already in the colour) by `smoothstep(gap / SoftParams.x)`. `SoftParams.x` is the soft-edge distance in world units, 0 = off, then the shader is the plain one (fade 1; the branch is on a constant). The engine's projection is right handed (`Projection[2][3]` = -1, near 6.3, far about 17,000 at the default camera), so the distance is `-P[3][2] / (depth * P[2][3] - P[2][2])`; the older `LRViewZ` helper of the low-resolution composite does not give a distance (it is only used there for relative weights). `TRampFlat` / `TRampAnimateFlat` techniques lie on the ground by design (they would fade away completely) and keep their hard edge; MODULATE*, REFRACT and TLight techniques, beams and trails are not touched.
- **Distance per level**: Low 1 world unit, High 3 (`kSoftDistance` in `ParticleLowRes.cpp`), times `ren_SoftParticleScale` (default 1; `FAF_SOFT_PARTICLES` and `FAF_SOFT_PARTICLE_SCALE` in the environment win over the console variables).
- **Depth**: the same sampled copy of the scene depth the half-resolution path uses (`Device::CopyDepthStencil` into a `DepthStencilTarget` created sampled, `EffectVariable::SetDepthStencil`; D3D11, D3D12, Vulkan), taken once per `RenderEffects` call, lazily, just before the first eligible bucket is drawn (`particlelowres::EnsureSoftDepth`), and kept bound until the end of the call. The particle pass writes no depth, so the copy stays valid for the half-resolution passes, which share it (a call with both runs one copy). Region `SoftDepth` in `FAF_GPU_PROFILE`. A copy the backend refuses turns the feature off for the session (a log line).
- **With the half-resolution path**: the low-resolution passes have their own (downsampled) depth buffer, which cannot be sampled while it is the depth test, so the `_LR` twins look the same scene copy up at the full-resolution pixel their low-resolution pixel is centred on (`LRView + position * LRRatio`).
- **Host test**: `faf_particle_tests` (patch text on a minimal source and on the real `particle.fx` with `FAF_STOCK_FX_DIR`: 24 low-resolution twins, 18 softened, flat techniques untouched, the soft shaders defined before the first technique that uses them).

## Post-process anti-aliasing

The Direct3D 11, 12 and Vulkan swap chains are flip-model, which cannot be multisampled, so the Anti-Aliasing dropdown of the options screen has no entries there (`head.mStrs` stays empty). Instead the finished 3D world is filtered before the interface is drawn into the same back buffer.

- **Modes** (`gpg::gal::PostProcessAAMode`, `src/gpg/gal/backends/common/PostProcessAA.h`): 0 Off (default), 1 FXAA, 2 SMAA. FXAA is FXAA 3.11 in the quality form: luma computed from the colour, 12 search steps, sub-pixel quality 0.75, edge threshold 1/6, minimum threshold 1/12; one pass, no constant buffer, the texel size comes from `GetDimensions`. SMAA 1x (mode 2) is a separate, three-pass implementation (see below); Options > Video offers Off, FXAA and SMAA.
- **Setting:** Options > Video > **Post-process Anti-Aliasing** (render feature `post_aa`, see above; only on D3D11, D3D12 and Vulkan, applies at once), the console variable `ren_AntiAliasing` (0 / 1 / 2) or `/aa off|fxaa|smaa` on the command line (the command line wins over the profile option). Default Off.
- **Where it runs** (`WRenViewport::Render`, `src/moho/app/WxRuntimeTypes.cpp`): per world view right after the water pass, before the playable-boundary and UI selection pass (`RenUI`, the unit selection brackets), before the mesh stages of the translucent things (shield bubbles, explosion and cloud meshes) and before the particle effects and the refracting effects, restricted to the view's pixel rectangle (`mScreenPos` / `mScreenSize`). So it sees only the opaque world: the brackets and other world-space UI are neither darkened nor treated as geometry, effects are not darkened by what is behind them, and the shield bubbles' depth-only `ShieldFill` pass (which writes the whole bubble sphere into the depth buffer) does not hide the ground under a bubble. Fixed 2026-10-28; before that the pass ran after the refracting effects and showed all three problems (a dark halo around the brackets, no occlusion under any shield, particles darkened). Orthographic views (minimap, cartographic) are skipped (logged once). The projection matrix of the view camera does the unprojection: the engine's cameras are right-handed with an *infinite far plane* (`m22 = -1`, `m23 = -1`), so depth = 1 + m32 / distance; the stored depth channel uses a fixed range of 8192.
- **Screen-space cap (2026-10-28).** The search radius in pixels is capped at 6 % of the view height. The world radius alone spans hundreds of pixels when the camera is close, which made a wide dark haze around every unit's base and doubled the cost (D3D12 High, 1600x900, 240 fps: 1.03 ms close up before, 0.54 ms after; zoomed out 0.5 ms both ways).
- **How:** `Device::ApplyPostProcessAA(head, mode)` copies the head's back buffer to a texture of its own and draws one full-screen triangle back into the back buffer. It saves and restores the bound targets, viewport and pipeline state. The copy is made again whenever the back buffer's size or format differs from it (resolution change, borderless, reset). D3D12: `DeviceD3D12::ApplyPostProcessAA`, DXC through the same effect shader compiler as the blit pipelines (no game file). D3D11: `DeviceD3D11::ApplyPostProcessAA`, `D3DCompile` `vs_4_0` / `ps_4_0`. Vulkan: `PostProcessAAVulkan.cpp`, one GPU program (the vertex-pulling path, texture at t4, sampler s0) and `GetRenderTargetData` for the copy. The pixel position (`SV_Position`), not the interpolated uv, addresses the source, because Vulkan draws through the viewport the engine shifts by half a pixel. D3D9 and D3D10 keep the base class answer (false, nothing drawn).
- **Cost** (RX 7900 XTX, 1600x900, the structures census scene `tests/lights/ingame/dynlights_census_structures.lua`, camera zoom 35, `FAF_GPU_PROFILE=600`, region `AntiAliasing`, copy and pass together): D3D12 0.057 ms per frame (0.037..0.066), D3D11 0.041 ms (0.030..0.094), Vulkan 0.13 ms (0.05..0.26; the extra transfer and layout changes of the GPU-program path).
- **Diagnostics:** `FAF_AA_SPLIT=1` leaves the left half of the screen unfiltered, so one frame shows before and after side by side; `FAF_AA_SPLIT=2` draws the filter's difference, amplified 4x (which pixels it changes: world edges only, the interface does not show up).
- **Verified (2026-10-26, in game, windowed 1600x900):** all three backends, the filter on the world's edges (staircases of unit, structure and ring edges become smooth gradients; a flat-colour area stays identical), the interface text and panels not changed (difference view), the copy recreated and the picture correct after `SC_PrimaryAdapter 1280,720,60` (borderless), `1920,1080,60` and `windowed` (1024x768). Not tested: exclusive full screen, a lost device, the Options > Video entry itself (the registry logs `render feature post_aa on d3d12: level 0`), D3D9 and D3D10.
- **Limits:** FXAA can soften thin high-contrast lines and the lifebars a little (they are world-space geometry, filtered with the world); it works on the final colour of the frame, so it cannot fix sub-pixel shimmer of thin geometry the way multisampling does. The filter reads the gamma-space colour the game draws, which is what FXAA 3.11 expects.

### SMAA 1x

Mode 2 of `ren_AntiAliasing`. One implementation for all three APIs in `gpg::gal::PostProcessPass` (`src/gpg/gal/PostProcessPass.{h,cpp}`), written against public `Device` calls only (the same approach as the ambient occlusion pass: `CreateRenderTarget`, `StretchRect`, `ClearTarget`, `SetViewport`, `CreateGpuProgram`, `DrawGpuProgram`); the HLSL is `src/gpg/gal/backends/common/PostProcessSmaa.h`. D3D9 and D3D10 keep their entries as before (the Post-process Anti-Aliasing option does not exist there; D3D9 has real multisampling).

- **Passes** (Jimenez et al. 2012): the back buffer is copied (`StretchRect`) into a working target, then (1) *edge detection* on luma (threshold 0.1, local contrast adaptation factor 2) into an RGBA8 target (left edge, top edge), (2) *blend weights*: for every pixel on an edge a point-fetch search of up to 16 pixels each way along the edge finds the two ends of the line and the edges that cross it there (up, down, both, none), and the coverage the line leaves in the pixel and in its neighbour is evaluated from that pattern and the pixel's place in the line, into a second RGBA8 target, (3) *neighbourhood blending* into the back buffer: one bilinear fetch towards the neighbour across the pixel's strongest edge (the blend weights follow the reference implementation's conventions). The working targets follow the back buffer's size and format and are made again when they change; the engine's bound targets and viewport are put back.
- **Not the reference lookup tables.** The reference implementation reads two pre-integrated textures (area, search). Here neither exists: the area under the line is the integral of a trapezoid and is computed per pixel in closed form (`SmaaCoverage`), and the search steps pixel by pixel with `Load` instead of the bilinear-fetch trick (it only runs on pixels that are on an edge). So no data file and no embedded table is needed. A line that bends the same way at both ends (a box edge) is blended only when it is shorter than a few pixels (the weight fades out between 1 and 9 pixels); a line whose far end the search does not reach counts as straight there and its weight tapers to nothing as the known end gets 16 pixels away, so the blend does not jump where the search gives up.
- **Not in this version:** the reference's diagonal pattern search and corner rounding. 45-degree lines are treated like any staircase (a quarter of the possible improvement: the host test measures 75 % of the aliased error left at slope 1, 12-30 % at slopes below 0.25 or above 4); corners of boxes are rounded a little within 16 pixels, as the reference does.
- **Cost** (RX 7900 XTX, 1600x900 windowed, the PP test scene `tests/postprocess/ingame`, game paused, `FAF_GPU_PROFILE=120`, region `AntiAliasing`, medians over 14-34 profile blocks per mode, the first two after a switch dropped; copy and three draws together; other sessions' games were running, so the single blocks scatter by +-0.05 ms and D3D11, whose timestamps are wall-clock based, has outliers of 1-2 ms): D3D12 0.10 ms per frame (two runs: 0.098 and 0.104; FXAA in the same runs 0.040 and 0.043), D3D11 0.049 ms (FXAA 0.032), Vulkan 0.057 ms (FXAA 0.045). SMAA is about 1.2 to 2.5 times the cost of FXAA and a tenth of a millisecond at most.
- **Compared with FXAA** (paused frames of the same scene, Off against the filter, maximum channel difference over every second pixel, 1600x900): FXAA changes 2.0 % of the pixels by more than 8 of 255 and 0.49 % by more than 24, SMAA 1.1 % and 0.27 %; the mean absolute difference is 0.65 and 0.31. The same figures on D3D11, D3D12 and Vulkan to within 0.05. In the enlarged crops SMAA turns the staircases of the orange range ring and of the unit and structure outlines into gradients as FXAA does, but the texture detail inside the units and on the ground stays as sharp as it was (FXAA smears it), and the lifebars keep their bodies (FXAA blurs the whole bar; SMAA rounds only the 16 pixels at each end). Images (crops of paused frames, 5x, left Off, middle FXAA, right SMAA): `docs/images/pp_ring_d3d12.png`, `pp_ring_d3d11.png`, `pp_ring_vulkan.png` (the range ring, a thin line), `pp_unit_d3d12.png` (a unit and its lifebars); `pp_sharpen_d3d12.png` shows SMAA, SMAA + Sharpen Low, SMAA + Sharpen High.
- **Host test** `tests/postprocess/PostProcessTests.cpp` (`faf_postprocess_tests`) runs the real shaders on a WARP Direct3D 11 device: a flat image and straight vertical / horizontal edges and the long sides of a box come out unchanged to 1/255; for slanted edges at nine slopes (0.0625 .. 4 and two negative) averaged over nine sub-pixel positions, the mean error against the exact pixel coverage drops to 12 % (slope 1/16), 28 % (1/4), 50 % (1/2), 75 % (1, the diagonal limit above), 30 % (4); the colour range is kept; a box corner is rounded and the blend along the edge fades without a step.

## Sharpening

Contrast adaptive sharpening (AMD FidelityFX CAS, 3x3 form) of the finished 3D world, a render feature of its own (`sharpen_quality`, Off / Low / High, `ren_SharpenQuality`, `/sharpen off|low|high`). It runs right after the post-process anti-aliasing (or alone) at the same place in `WRenViewport::Render`, before the UI, in the profile region `Sharpen`; it is a copy of the back buffer and one full-screen pass of `gpg::gal::PostProcessPass::ApplySharpen` (the `SharpenLowPS` / `SharpenHighPS` shaders of `PostProcessSmaa.h`).

- **What it does:** a negative lobe on the four neighbours whose strength follows the headroom of the local range (the plus-shaped and the 3x3 minimum and maximum added, as CAS does): flat areas are not touched, full-contrast edges are not touched (no halos), soft edges gain contrast. Low is sharpness 0.35, High 0.8 (lobe weight -1/lerp(8, 5, sharpness)).
- **Per API:** D3D11, D3D12 and Vulkan through the GPU-driven programs (like the ambient occlusion pass). D3D9 is registered unsupported with a reason: it draws with the shipped shaders and the renderer has no post-process stage or render-target copy there to run the pass in (a D3D9 version would need both; the anti-aliasing dropdown of D3D9 is real multisampling and unaffected). D3D10 does not start.
- **Cost** (same runs, region `Sharpen`, medians, copy and one draw): D3D12 0.021-0.049 ms per frame (median over three runs 0.032), D3D11 0.019 ms, Vulkan 0.029-0.042 ms.
- **Effect** (same frames, Off against the setting): Low changes 3.6 % of the pixels by more than 8 of 255 (together with SMAA), High 11 % (alone 11.4 %; mean absolute difference 4.1); more than 24 levels only at 0.3-0.5 % (the edges). It also brings out the grain of the ground texture (it reads as detail), which is the price of High.
- **Limits:** it works on the gamma-space colour with no knowledge of what is geometry and what is texture; the world-space overlays are sharpened with the world (they are in it), the UI is not (it is drawn later). Applies at once; never touches the simulation.
- **Verified (2026-10-27, in game, windowed 1600x900, `adaptive_acid_lakes`, the PP test scene, game paused, modes Off / FXAA / SMAA / SMAA + Sharpen Low / SMAA + Sharpen High / Sharpen High / Off cycled live with `ren_AntiAliasing` and `ren_SharpenQuality`):** D3D11, D3D12 and Vulkan draw the passes (log: `Post-process anti-aliasing mode 2 active`, `Sharpening level 1 active`), same-scene pictures agree between the three APIs. Not verified: a resize with the passes on (the swap-chain recreation of `SC_PrimaryAdapter` was refused with E_ACCESSDENIED in that environment, before any of the new code ran; the targets follow the back buffer's size by the same check as the ambient occlusion pass), exclusive full screen, a lost device, split screen, the Options > Video entries themselves (the registry logs `render feature sharpen_quality on d3d12: level 0 (off)`), the `/aa smaa` and `/sharpen` command lines (passed on, the console variables were what the test switched), D3D9, other GPUs.

## Ambient occlusion

Screen-space ambient occlusion darkens the finished 3D world where geometry closes in: the feet of buildings, the gaps between units, the creases of a unit's own parts. Render only; nothing touches the simulation.

- **Algorithm** (`src/gpg/gal/backends/common/AmbientOcclusion.h`, HLSL shared by D3D11, D3D12 and Vulkan): ground-truth AO (GTAO, Jimenez et al. 2016) from the scene depth alone. The view-space normal comes from depth differences (the nearer neighbour on each axis, so silhouettes do not smear); per pixel `slices` screen directions (rotated inside a 4x4 Bayer pattern) are searched `steps` taps to each side up to `ren_AORadius` world units away (quadratic spacing, falloff towards the radius) and the horizons are integrated against the normal. Depth is `Load`-ed, never filtered. Two blur passes (5 taps with weights 0.5 1 1 1 0.5, one period of the noise pattern) whose weights drop at depth edges (relative depth difference above 2.5 %) remove the pattern; the second one runs at back buffer resolution and upsamples a half-resolution target depth-aware. The result is blended as black with alpha = 1 - occlusion (a plain alpha blend, colour x occlusion; the back buffer's alpha is not written).
- **Levels** (`AmbientOcclusionQualityFor`): Low 2 directions x 4 steps at half resolution; Medium 3 x 5 at half resolution; High 3 x 6 at full resolution. `ren_AOHalfRes` -1 (default) takes the level's choice, 0 / 1 force full / half.
- **Setting:** Options > Video > **Ambient Occlusion** (render feature `ambient_occlusion`, only on D3D11, D3D12 and Vulkan, applies at once), the console variable `ren_AmbientOcclusion` (0..3) or `/ao off|low|medium|high` on the command line. Default Off. Tuning variables: `ren_AORadius` (world units, 1.5), `ren_AOIntensity` (1), `ren_AOPower` (1.6, contrast), `ren_AOHalfRes`.
- **Depth, per API.** The shipped terrain and mesh shaders write depth into the head's depth buffer and expose nothing else, so the pass reads that buffer itself: the head depth target (D24S8) is now created *sampled* on D3D11 (typeless texture plus an `R24_UNORM_X8_TYPELESS` view), D3D12 (the same; the resource moves to a shader-read state for the pass and back to depth-write at the engine's next target bind) and Vulkan (usage `SAMPLED` and a second, depth-aspect-only image view; layout `DEPTH_STENCIL_READ_ONLY_OPTIMAL` for the pass). No copy or resolve is needed. D3D9 (depth sampling is vendor specific and the shipped shaders are shader model 2) and D3D10 (does not start) are registered unsupported with a reason.
- **How.** One implementation for all three APIs in `gpg::gal::AmbientOcclusionPass` (`src/gpg/gal/AmbientOcclusionPass.{h,cpp}`), written against public `Device` calls only (render targets, `SetViewport`, `ClearTarget`, `CreateGpuProgram`, `DrawGpuProgram`: the GPU-driven programs of `GpuDriven.h`). The backends only had to learn to bind a depth or colour target as `t4` / `t5` (`GpuBindings::depthTextures` / `renderTextures`). Three draws: the horizon search into an `R16G16_UNORM` target (occlusion, view depth / far), the horizontal blur into a second one, the vertical blur and composite into the back buffer. The targets follow the back buffer size (recreated on resize); the bound targets and viewport are put back.
- **Where it runs** (`WRenViewport::Render`, `src/moho/app/WxRuntimeTypes.cpp`): per world view after the refracting effects (terrain, meshes, water and effects have written their depth), before the view's overlays (life bars, selection brackets) and the UI, restricted to the view's pixel rectangle (`mScreenPos` / `mScreenSize`). Orthographic views (minimap, cartographic) are skipped (logged once). The projection matrix of the view camera does the unprojection: the engine's cameras are right-handed with an *infinite far plane* (`m22 = -1`, `m23 = -1`), so depth = 1 + m32 / distance; the stored depth channel uses a fixed range of 8192.
- **Cost** (RX 7900 XTX, windowed 1600x900, skirmish on adaptive_acid_lakes with structures of four factions and unit clusters, game paused, `FAF_GPU_PROFILE=300`, region `AmbientOcclusion`, three draws): D3D12 High about 0.65-0.95 ms per frame, Medium 0.5-0.65 ms, Low 0.35-0.55 ms; D3D11 High 0.2-0.55 ms, Vulkan High 0.4-0.8 ms. The GPU clock was not pinned, so the spread is as large as the difference between levels (and D3D11's timestamps are wall-clock based). The blur and composite passes at back buffer resolution cost about as much as the half-resolution search, which is why Low is not much cheaper than Medium.
- **Verified (2026-10-27, in game, windowed 1600x900, same scene, paused, `ren_AmbientOcclusion` switched 0 / 3 every few seconds, frames dumped with `FAF_GAL_DUMP_SECONDS=1`):** D3D11, D3D12 and Vulkan draw the pass (3 draws); the frame mean falls from 59.5 to 58.2 on all three and the mean absolute per-pixel difference is 1.20 / 1.23 / 1.25 (D3D12 / D3D11 / Vulkan). The darkening sits at the feet of structures and in the creases of the ACU; flat ground, the sky and the interface are unchanged. `SC_PrimaryAdapter 1280,720,60`, `1920,1080,60` and `windowed` with the pass on (Medium half and High full resolution): the targets are recreated for the new size on all three APIs, no crash. Host test `tests/ao/AmbientOcclusionTests.cpp` (`faf_ao_tests`) runs the real shaders on a WARP device over synthetic depth buffers: open ground stays above 0.97, the ground at a box's foot drops to 0.76-0.78, the box's wall is 0.65-0.75 at its foot against 0.995 higher up, the roof and the sky stay open, half and full resolution agree to 0.002 mean difference.
- **Limits.** It darkens the finished colour (sun, specular and emission too), so a strong setting looks like dirt in the creases rather than missing ambient light; translucent effects and the water surface are darkened by the occlusion of what is behind them; thin objects get no special handling (no thickness heuristic); the screen-space search sees nothing outside the screen or hidden behind objects. Not verified: exclusive full screen, a lost device, split screen (more than one world view), the Options > Video entry itself (the registry logs `render feature ambient_occlusion on <api>: level 0`), D3D9 (unsupported by design) and D3D10, other GPUs.

## Frame rate limit

A cap on the frames per second, for power, heat and fan noise, and against the coil whine some graphics cards make when they run at a few hundred frames per second. CPU pacing only, so it is the same on every API and never touches the simulation.

- **Where:** `src/moho/render/FrameLimiter.{h,cpp}`; `CD3DDevice::Paint` calls `FrameLimiterWait()` right after `Present`. The frame times sit on a fixed grid (a slow frame does not shift the later ones; more than one interval late restarts the grid instead of racing to catch up). The wait is a high-resolution waitable timer for the bulk and a spin of the last 0.4 ms; on a system without that timer it sleeps in milliseconds and then spins.
- **Setting:** Options > Video > **Frame Rate Limit** (render feature `fps_limit`, levels Off / 30 / 60 / 90 / 120 / 144 / 165 / 200 / 240, default Off), the console variable `ren_FpsLimit` (the level), `ren_MaxFps N` (any value, wins over the level, 0 = use the level) or `/maxfps N` on the command line.
- **Vsync:** with vsync on, the display's refresh rate paces the frames too: the frame that misses a vblank waits for the next one. A limit that divides the refresh rate (a half, a quarter) keeps them evenly spaced; others still work (below).
- **Verified (2026-10-28, windowed 1600x900, 240 Hz display with vsync, static scene, `FAF_GPU_PROFILE=120`, wall time per frame):** D3D12 off 4.18 ms (239 fps), 60 fps 16.5 ms (60.5), 120 fps 8.4 ms (119.5), exact 45 fps 22.0 ms (45.4), 30 fps 32.3 ms (30.9); D3D11 and Vulkan agree to within 1 fps (Vulkan 60 gives 59.2). Back to off: 239 fps again. The Options entry itself was not clicked (the log shows `render feature fps_limit on <api>: level 0 (off)` on all three). Not tested: D3D9, split screen, a window on a monitor of another refresh rate.

## Stratum mask resolution

The map file stores the stratum masks (the two `_utilitya_mask` / `_utilityb_mask` textures that blend the eight terrain layers) at whatever size the mapper saved them. `CWldTerrainRes::Finalize` used to copy both into new dynamic sheets of exactly half the map's size (`(heightfield width - 1) / 2`), and that copy is a resample on every API (Direct3D 11, 12 and Vulkan re-encode the source into the destination's size), so a mask saved at a higher resolution was reduced to that preset: a 40 km map (2048) kept 1024 of its 2048, an 81 km map 2048 of 4096.

- **Now (`src/moho/terrain/StratumMaskSize.h`, one axis):** a mask keeps the size it was saved with, but never less than half the map's size (a coarser mask is raised to it, as before) and never more than `max(2048, 2 x map cells)`, with an absolute ceiling of 8192. So 2048 is allowed on any map (10 km, 20 km), 4096 only on a 40 km map or larger, and **8192 only on an 81 km map**. The rules are `static_assert`s in the header and are checked at every build. `mStratumMaskWidth` / `Height` follow mask 0. The log has one line per map: `Terrain: stratum masks 2048x2048 and 2048x2048 (saved in the map as ...; half the map is 1024x1024, the most 4096x4096)`.
- **Debug switches:** `FAF_STRATUM_MASK_SIZE=half` restores the old size, a number N forces N x N. `FAF_STRATUM_MASK_TEST=1` replaces the loaded masks with a fine test pattern before the copy (the loaded sheets are not lockable, so a lockable sheet of the same size takes their place as the copy's source): 64-texel tiles, each with one-texel vertical stripes, one-texel horizontal stripes, a four-texel checker or a one-texel diagonal hatch, so there are hard edges and detail down to one texel. It stands in for a mapper's detailed mask.
- **Verified (2026-10-28, D3D12, Setons Isle 40 km, saved masks 2048, camera on the tile corners, `FAF_STRATUM_MASK_TEST=1`, same build, only `FAF_STRATUM_MASK_SIZE=half` differs):** with 2048 sheets the pattern is in the picture, the dot hatch, the stripes and the hard tile edges; with the old 1024 sheets the same ground is smooth, the one-texel detail is averaged away and only the soft outline of the tiles is left. Mean difference between the two builds 11 to 30 levels at the five spots. Caps read from the log: 10 km (Corona) 256 saved, at most 2048; 20 km 512 saved, at most 2048; 40 km 2048 saved, at most 4096; 81 km (MKLOUD1) 4096 saved, at most 8192; all load. Memory: two RGBA8 sheets, 32 MB at 2048, 128 MB at 4096, 512 MB at 8192.
- **Earlier checks that showed nothing (do not repeat):** a first comparison on Holy Lands compared 1024 and 2048 sheets and found no difference, but that map's terrain layers do not resolve to real textures (everything falls back to one sand texture, so no mask has any effect), and the first version of the test pattern was never written (the loaded mask is not lockable, the log line said so). Use a map with working terrain layers, for example Setons Isle, and check the log for `test pattern written`.
- **Not tested:** a real map whose mapper painted at a higher resolution than half the map (none in the maps folder with fine detail was at hand); D3D11 and Vulkan with the pattern (they load the 40 km map; the copy is the same code).
- **Not changed:** the water map and the water masks stay at half the map's size, and the editing calls (`UpdateStratumMask`, `GetStratumMask`, only used by the map editor) take their rectangle from the mask 0 size.

## Render scale

Draws the 3D world at a fraction of the window and upscales it before the interface, which is drawn at native resolution: the escape hatch for weak GPUs and for 4K. Render only; the camera, the simulation, mouse picking and every projection are untouched.

- **Setting:** Options > Video > **Render Scale** (render feature `render_scale`, D3D11, D3D12 and Vulkan, applies at once), the console variable `ren_RenderScale` (0 = 100 %, 1 = 85 %, 2 = 75 %, 3 = 67 %, 4 = 50 %) or `/renderscale 100|85|75|67|50` on the command line (wins over the profile). `ren_RenderScaleSharpness` (0..1, default 0.6) is the strength of the sharpening after the upscale; -1 is a diagnostic that shows the scaled world's texels unfiltered (no upscale filter, no sharpen). Default 100 %: nothing changes, no target is made. D3D9 is registered unsupported (it has no GPU program path to upscale with, and real multisampling; lower the resolution instead), D3D10 does not start.
- **How the world is redirected** (`src/moho/render/RenderScale.{h,cpp}`, hooks in `WRenViewport::Render`, `src/moho/app/WxRuntimeTypes.cpp`): seen from the world pass the engine simply runs in a smaller window. For the world loop the head's colour and depth lanes of `CD3DDevice` (`mRenderTargetLocks` / `mDepthStencilLocks`) and the viewport's three frame-sized lanes (terrain normals / frame copy for refraction, the reflection target, and their depth: `mPrimaryTargetLocks`, `mSecondaryTargetLocks`, `mDepthStencilLocks`) are replaced by scaled targets, and `UpdateRenderViewportCoordinates` hands out the view rectangle and the target size scaled together (`mScreenPos`, `mScreenSize`, `mFullScreen`), so the terrain's viewport scale/offset constants, the water refraction lookups, the reflection pass, ambient occlusion and the half-resolution particles (which size themselves from the bound target) all work unchanged. Nothing in the camera changes, so the projection and the mouse-to-world path stay what they were. The frames drawn at the start of the frame (`UiFrames`) go to the native back buffer first; the scaled targets are cleared at the start of the loop.
- **Where the upscale runs:** per view, right after the world of that view (opaque, water, effects, refraction, ambient occlusion, selection brackets and range rings) and *before* the view's overlay pass (`worldView->mView->Render`: life bars, names, strategic icons, command overlays) and the debug canvases, so those are drawn at the window's size and stay sharp. The cartographic view, dynamic-lights debug view, FXAA, the control tree, bloom and the rest of the frame follow at native size. The frame dump (`dump_Frame`) draws at full size while it runs. The profile region is `RenderScale`.
- **Targets** (`gpg::gal::RenderScalePass`, `src/gpg/gal/RenderScalePass.{h,cpp}`, written against public `Device` calls only like the ambient occlusion pass): the scaled colour target (format 2) and a *sampled* depth target (so ambient occlusion can still read it; while the loop runs `gpg::gal::WorldOutputContext` names them for passes that ask for "the head's" targets), size `ceil(window * factor)`, recreated when the window size or the level changes and released with the device (`D3DWindowOnDeviceExit`). Level changes need no restart.
- **The upscaler** (`src/gpg/gal/backends/common/RenderScale.h`, one HLSL source for the three APIs, `Load` only): our own edge-adaptive spatial filter. The 4x4 source texels around a pixel are weighted with a Lanczos-2 shaped kernel whose axes follow the local structure (a structure tensor of the luma, blended bilinearly from the four central texels): stretched along an edge, tightened across it, so a diagonal edge is reconstructed as a line and not a staircase; the result is clamped to the range of the four nearest texels, so it cannot ring. Then a contrast-adaptive 5-tap sharpen on the upscaled image (the negative lobe is limited per pixel by what the neighbours can take without leaving 0..1, the least of the three channels, so flat areas and pure black / white edges get nothing). It is not FSR; the structure is similar (an edge-adaptive upscale plus a contrast-adaptive sharpen) and all the code is new.
- **Host test** `tests/renderscale/RenderScaleTests.cpp` (`faf_renderscale_tests`, the real shaders on a WARP device): flat areas stay flat (< 0.002), no value leaves the source range, a ramp stays monotonic, a diagonal edge is reconstructed with 13 % (50 %), 8 % (67 %) and 9 % (85 %) of the mean squared error of bilinear filtering against the full-resolution truth, an offset view rectangle gives the identical picture and leaves the rest of the target untouched, the sharpen pass steepens a soft edge (10-90 % rise 4.8 -> 4.5 px at full strength), leaves plateaus and pure black / white edges alone, and strength 0 is the identity. Plus the extent and rectangle arithmetic.
- **Cost** (RX 7900 XTX, `FAF_GPU_PROFILE=120`, the staged battle scene, game paused; "GPU" is the profiler's whole-frame GPU time, first command to Present; the 1600x900 scene is light and partly CPU bound, so its differences are small and noisy, the 4K ones are the real figures): D3D12 at 3840x2160: 100 % 8.32 ms, 67 % 6.72 ms (-19 %), 50 % 5.23 ms (-37 %); the upscale and sharpen cost 0.44 ms at 67 % and 0.35 ms at 50 %. D3D12 at 1600x900: 3.45 / 3.11 / 2.77 ms (100 / 67 / 50 %), the resolve 0.10-0.18 ms. Vulkan at 3840x2160: 4.33 / 3.47 / 2.23 ms (-20 % / -48 %), resolve 0.27-0.31 ms. D3D11 at 3840x2160: wall time per frame 11.8 ms at 100 % against 5.8 ms at 67 % and 50 % (its GPU timestamps are not usable and the lower levels hit another limit, so read it as 'at least 2x'). At 1600x900 (a light scene): D3D11 2.3 / 2.1 / 1.0 ms, Vulkan 5.5 / 5.6 / 5.2 ms (noisy, CPU bound). These were measured before the per-view split (resolve before the overlay) was added; that changes only where the resolve sits.
- **Verified (2026-10-27, in game):** D3D11, D3D12 and Vulkan, windowed 1600x900 (D3D12 also 3840x2160): all five levels switched live with `ren_RenderScale` while paused, the log line `Render scale: world drawn at WxH for a ... window` appears for each; paired frames (`FAF_GAL_DUMP_SECONDS=1`) show the same picture at every level, the interface (panels, text, icons) unchanged, the unit names, life bars and icons sharp, terrain, units and shadows softer by the expected amount; the frame's Laplacian energy follows the same sequence of values on all three APIs (so the picture is the same on all three); `/renderscale 67` on the command line; `SC_PrimaryAdapter 1280,720,60`, `1920,1080,60` and `windowed` with 67 % active on all three APIs (targets recreated, no crash, correct picture); together with FXAA (`/aa fxaa`) and High ambient occlusion on D3D12 (the occlusion targets follow the scaled size and the scaled depth: `Ambient occlusion: 1067x600 occlusion targets for a 1067x600 view`).
- **Limits and not verified:** the world-space overlays drawn inside the loop (selection brackets, the terrain-bound lines) are part of the scaled world and get as soft as it; a 1-pixel world line loses contrast at 67 % because the information is not in the smaller image (the upscaler cannot recover a line narrower than a source texel). **Fixed 2026-10-28:** the terrain normal basis pass (`TransformTerrainNormals`, a full-screen `TCreateBasis` quad) was sized from the window instead of the scaled lane, so it filled the scaled target with a zoomed, misaligned part of the normal buffer and the ground's lighting was smeared into blotchy patches at 67 % and 50 % (the diagnostic above showed it was already in the scaled texels, not in the upscaler); it now uses the scaled size. The range rings are another exception (fixed 2026-10-28): their band thickness is divided by the scale (`REN_GetWorldDrawScale`), because a band thinner than a source texel was kept only in some pixels and the ring turned into dots; the ring now keeps its width in source texels (a little wider in the final picture, continuous). Texture sampling keeps the engine's mip bias, so fine ground detail is blurrier than a 100 % picture downsampled to the same size would be; a negative bias (as temporal upscalers use) is not applied. Not tested: exclusive full screen, a lost device, split screen (more than one world view; the code resolves per view and keeps one scaled target), the Options > Video entry itself (the registry logs `render feature render_scale on <api>: level 0`), D3D9 (unsupported by design) and D3D10, other GPUs, the engine's screenshot key, mouse picking at a reduced scale (unchanged by construction, not clicked), a GPU-bound 4K scene on D3D11 (timestamps unusable).

## Anisotropic filtering

Forced anisotropic texture filtering (`src/gpg/gal/ForcedAnisotropy.h`, `src/moho/render/AnisotropicFilter.cpp`; render feature `aniso_quality`, console variable `ren_Anisotropy` 0..4 = Off, 2x, 4x, 8x, 16x). The shipped effects pick their own samplers, nearly all trilinear, so ground, decals and units blur at grazing angles. Nothing in the game data changes: each backend rewrites the sampler it builds for an effect.

Rule (`ForceAnisotropicFilter` / `ForceAnisotropicSampler`): a 2D effect sampler with a linear min and mag filter (trilinear or bilinear) becomes `ANISOTROPIC` with the chosen maximum. Left alone: point and mixed filters, comparison (shadow) samplers, samplers that already are anisotropic, mip-less samplers (`MaxLOD` 0), the engine's own blit / post-process / GPU-driven samplers, samplers whose names mark a lookup table (`dynLight*`, `*lookup*`, `anisotropic*`, `*ramp*`, `fresnel*`, `falloff*`), cube and volume textures, and, on every API except Direct3D 9, any sampler whose texture variable currently holds a render target (shadow maps and blurs, reflection / refraction, frame buffers) or a texture without a mip chain. With Off the effects' own states are used unchanged.

| API | Where | Live change | Texture-aware |
|---|---|---|---|
| Direct3D 9 | `StateManagerD3D9::SetSamplerState`: linear MIN / MAG filters become anisotropic and `MAXANISOTROPY` is set, for pixel samplers 0..15 | yes (the cache keeps what the device holds) | no: the state manager does not know the texture, so render-target reads also go anisotropic (1:1 reads look the same) |
| Direct3D 11 | Effects 11: `ID3DX11EffectSamplerVariable::SetSampler` with an anisotropic copy of the effect's state, `UndoSetSampler` to give it back. Which sampler reads which texture variable comes from the effect source (preprocessed, translated and parsed as the D3D12 / Vulkan runtimes do, `DeviceD3D11::SamplerTextures`); `EffectVariableD3D11::SetTexture / SetRenderTarget` report whether the variable holds a world texture (`TextureD3D11::IsWorldTexture`) | yes (`EffectSamplersD3D11::Sync` at technique begin) | yes |
| Direct3D 12 | `DeviceD3D12::SamplerTable(samplers, mask)`: the program's sampler table is built for the samplers whose bound texture is a world texture (`UpdateAnisotropicSamplers`, at the texture-table rebuild). Tables with a forced sampler live at the back of the 2048-descriptor sampler heap and are dropped whole, after a GPU wait, when the heap is full (`ResetForcedSamplerTables`); programs rebuild theirs when the generation changes | yes | yes |
| Vulkan | `DeviceVulkan::SamplerFor(desc, worldTexture)` with the same mask (`UpdateAnisotropicSamplers`); needs `samplerAnisotropy` (every desktop GPU) | yes | yes |
| Direct3D 10 | not reachable: the renderer does not start | - | - |

Notes:

- A Direct3D 12 sampler heap holds 2048 descriptors, 32 tables of the 64 the root signature needs. A first version that cached forced tables in the permanent map hung the game (the heap filled after a few level changes); the end region is why switching levels back and forth is safe.
- The profile stores the state key (`x4`), and the options module writes a feature's default into the profile the first time the options are built, so a changed default only reaches profiles that never saw the option.
- `FAF_ANISO_LOG=1` logs every sampler that gets forced (`Aniso: forced 16x on sampler Stratum0AlbedoSampler (texture Stratum0AlbedoTexture)`, Direct3D 11 and 12).
- Host test: `cmake --build --preset clang-x64-release --target faf_aniso_tests` (`tests/aniso/AnisotropyTests.cpp`, the filter, level, epoch and data-sampler rules).

The forced samplers on D3D11 and D3D12 are the same 39 (strata albedo and normal, terrain decals, skirts, mesh albedo / normals / specular, particles, ...); none of the render-target samplers.
